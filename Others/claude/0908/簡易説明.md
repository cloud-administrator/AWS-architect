## 2. 取得方式と重要な制約

### 取得対象

Activity Feedだけで本文を取得済みとは扱わず、チャットメッセージ、プロジェクト詳細、プロジェクト文書をそれぞれのAPIから取得します。チャット・プロジェクトの一覧取得APIは組織で絞り込み、現在の在籍者一覧を起点にしません。([Claude Platform][1])

| 対象                | この実装で保存するもの                                |
| ----------------- | ------------------------------------------ |
| Activity Feed     | Activityオブジェクト全体                           |
| チャット              | ユーザー入力、Claudeの回答、返されたツール入出力、参照情報を含むレスポンス全体 |
| プロジェクト            | 説明、カスタム指示、添付一覧                             |
| **project_doc**   | **contentを含むレスポンス全体**                      |
| Artifact          | メッセージに現れる各`version_id`のメタデータ               |
| アップロードファイル・生成ファイル | 参照情報とメタデータ。ファイル実体は取得しない                    |

`project_doc`は除外しません。一方、ファイルやArtifactのダウンロード用`/content`エンドポイントは呼びません。取得したメッセージなどに含まれるファイル参照は、そのまま保存します。([Claude Platform][1])

ただし、ツール引数やユーザー入力にファイル内容・Artifact生成コードが直接含まれる場合、そのテキストは本文として残します。そこを削ると、本文・ツール入出力の保存とraw保存の要件を満たせなくなるためです。

### ツール入出力

次を指定しています。

```text
tool_use_input_max_chars=-1
tool_result_max_chars=-1
```

公式仕様では、それぞれ既定の10,000文字制限を解除する指定です。ただし、API側のその他の上限まで無条件に解除されるとは保証されていません。`truncated=true`が返った場合は、対象IDとともに取得制約として記録します。また、ツール結果の一部非テキスト要素はAPIから省略される仕様です。([Claude Platform][2])

### 本文のTailは「全件再照合型」

**本文は、毎回対象組織を全件再照合し、同一レスポンスの重複保存を避ける方式です。変更分だけをAPIから取得する方式ではありません。**

公式には`updated_at`による差分取得があります。しかし、すべての子文書・本文の変更が親の更新時刻に確実に反映されるという保証を確認できなかったため、その前提には依存しない設計にしました。([Claude Platform][1])

この方式なら同じIDも取り直せますが、API呼び出し回数は増えます。**日次で一巡できるデータ量かどうかは、本番前に計測が必要です。**

シークレットチャットはEnterpriseのCompliance APIに含まれる公式仕様です。本実装ではシークレット・非公開・`user=null`を理由に除外しません。ただし、退職者や削除済みユーザーの個別データが実際に残っているかは、APIから取得できた結果で判断します。([Claudeヘルプセンター][3])

## 3. 対応環境とキーの権限

対応環境は、**Windows／PowerShell 7.6 LTS／ローカルNTFSのCドライブ**です。PowerShell 7.6は公式のLTS系列です。Windows PowerShell 5.1の`powershell.exe`ではなく、`pwsh.exe`を使用します。追加のPowerShellモジュール、Anthropic SDK、Python、データベースは不要です。([Microsoft Learn][4])

キーに必要なのは、指定された次の二つだけです。

```text
read:compliance_activities
read:compliance_user_data
```

`delete:compliance_user_data`は使用しません。組織一覧や組織設定をAPIで取得せず、対象UUIDを設定するため、`read:compliance_org_data`も不要です。キー自体が対象組織を読み取れる範囲を持っていることは、管理者が確認してください。([Claude Platform][5])

**対象UUIDは実際のワークロード組織のUUIDを指定します。親組織のUUIDから配下を自動展開する実装ではありません。** 複数組織なら、対象UUIDをすべて設定します。

## 4. 保存先とアクセス権の準備

専用実行アカウントを用意してください。以下では例として`CONTOSO\svc_claude_collect`を使用します。

次は、**管理者として起動したPowerShellで、まだ存在しない保存先を準備する例**です。既存フォルダーがあれば停止します。

```powershell
$ErrorActionPreference = 'Stop'
$Root = 'C:\ClaudeComplianceCollector'
$Account = 'CONTOSO\svc_claude_collect'  # 実際の実行アカウントに変更

if (Test-Path -LiteralPath $Root) {
    throw '保存先が既に存在します。既存データとACLを確認してください。'
}

New-Item -ItemType Directory -Path $Root | Out-Null

& icacls.exe $Root /inheritance:r /grant:r `
    '*S-1-5-18:(OI)(CI)(F)' `
    '*S-1-5-32-544:(OI)(CI)(F)' `
    "${Account}:(OI)(CI)(RX)"
if ($LASTEXITCODE -ne 0) { throw 'Root ACL設定失敗' }

foreach ($Name in @('bin','config','data','state','logs','staging')) {
    New-Item -ItemType Directory -Path (Join-Path $Root $Name) | Out-Null
}

foreach ($Name in @('data','state','logs','staging')) {
    & icacls.exe (Join-Path $Root $Name) /grant:r "${Account}:(OI)(CI)(M)"
    if ($LASTEXITCODE -ne 0) { throw "ACL設定失敗: $Name" }
}

[IO.File]::WriteAllBytes(
    (Join-Path $Root 'collector.lock'),
    [byte[]]::new(0)
)

& icacls.exe (Join-Path $Root 'collector.lock') /grant:r "${Account}:(M)"
if ($LASTEXITCODE -ne 0) { throw 'ロックファイルACL設定失敗' }
```

この例では、SYSTEMとAdministratorsにフルアクセス、実行アカウントにプログラム・設定の読取り権限と、データ・状態・ログの変更権限を付与します。`icacls`の継承・権限付与オプションはMicrosoft公式仕様に基づいています。([Microsoft Learn][6])

管理者がファイルを配置します。

```text
C:\ClaudeComplianceCollector\bin\Collect-ClaudeCompliance.ps1
C:\ClaudeComplianceCollector\bin\Check-ClaudeComplianceHealth.ps1
C:\ClaudeComplianceCollector\bin\Test-CollectorOffline.ps1
C:\ClaudeComplianceCollector\config\collector.config.json
```

収集タスクに常時管理者権限を与える構成にはしていません。保存データは平文のJSONなので、一般利用者からの読取り禁止、端末保護、ディスク・バックアップの暗号化も運用側で整えてください。

## 5. 環境変数の設定

**タスクを実行するのと同じWindowsアカウントで**PowerShell 7.6を起動し、次を実行します。

キーをコマンドに直接書かず、非表示の入力欄から設定します。

```powershell
# 実行アカウント名だけを確認
[Security.Principal.WindowsIdentity]::GetCurrent().Name

$SecureKey = Read-Host 'Compliance Access Keyを入力' -AsSecureString
$Pointer = [IntPtr]::Zero

try {
    $Pointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($SecureKey)

    [Environment]::SetEnvironmentVariable(
        'ANTHROPIC_COMPLIANCE_ACCESS_KEY',
        [Runtime.InteropServices.Marshal]::PtrToStringBSTR($Pointer),
        [EnvironmentVariableTarget]::User
    )
}
finally {
    if ($Pointer -ne [IntPtr]::Zero) {
        [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($Pointer)
    }
    $SecureKey.Dispose()
}

# キーではなく、設定済みかどうかだけを表示
-not [string]::IsNullOrWhiteSpace(
    [Environment]::GetEnvironmentVariable(
        'ANTHROPIC_COMPLIANCE_ACCESS_KEY',
        [EnvironmentVariableTarget]::User
    )
)
```

最後が`True`なら、そのアカウントのUser環境変数から値を読み取れています。

スクリプトも起動ごとにUserスコープを明示して読みます。管理者など**別アカウントのUser環境変数に設定しても、タスク実行アカウントの設定にはなりません**。MicrosoftはUser／Machine環境変数の永続化と、スコープを指定した読取り方法を文書化しています。([Microsoft Learn][7])

なお、User環境変数は秘密保管庫ではありません。Anthropicはキーの秘密管理サービスでの保管を推奨しています。本件では環境変数方式を採用するため、専用アカウントの保護を前提にしてください。([Claude Platform][5])

### 設定

同梱JSONの`REPLACE_WITH_ORGANIZATION_UUID`を実際のUUIDへ置き換えます。未変更なら停止します。キーは書きません。

```json
{
  "OrganizationUuids": [
    "REPLACE_WITH_ORGANIZATION_UUID"
  ],
  "KeyEnvironmentVariable": "ANTHROPIC_COMPLIANCE_ACCESS_KEY",
  "KeyEnvironmentScope": "User",
  "RequestsPerMinute": 120,
  "ActivityPageSize": 1000,
  "ChatPageSize": 100,
  "MessagePageSize": 20,
  "ProjectPageSize": 100,
  "LagSeconds": 120,
  "OverlapMinutes": 10,
  "MaxRetries": 6,
  "TimeoutSeconds": 120,
  "MaxRunMinutes": 1200

```

120 requests/min、再試行6回、実行上限20時間は、この実装の初期値です。

確認した公式レート制限は、使用するCompliance APIについて**親組織あたり600 requests/minで、キー・リンク組織・エンドポイント間で共有**です。スクリプトは全取得を直列化し、設定間隔、rate-limitヘッダー、429の`retry-after`で制御します。他の収集ツールがある場合、その利用分も含めた予算配分が必要です。([Claude Platform][8])

実キー・実ネットワークを使用しないテストを、まず実行します。

```powershell
& 'C:\Program Files\PowerShell\7\pwsh.exe' -NoLogo -NoProfile -NonInteractive `
  -File 'C:\ClaudeComplianceCollector\bin\Test-CollectorOffline.ps1'

```

すべてのassertionが`PASS`となり、終了コードが`0`であることを確認してください。**テストは同梱していますが、こちらでは実行済みではありません。**

### Backfill

```powershell
& 'C:\Program Files\PowerShell\7\pwsh.exe' -NoLogo -NoProfile -NonInteractive `
  -File 'C:\ClaudeComplianceCollector\bin\Collect-ClaudeCompliance.ps1' `
  -Mode Backfill `
  -ConfigPath 'C:\ClaudeComplianceCollector\config\collector.config.json'

$LASTEXITCODE
```

初回が時間上限などで終わらなければ、**同じBackfillコマンドを再実行**します。checkpointや既存データを削除してやり直す必要はありません。

### Tail

初回の監査・本文の両方が一巡した後に実行します。

```powershell
& 'C:\Program Files\PowerShell\7\pwsh.exe' -NoLogo -NoProfile -NonInteractive `
  -File 'C:\ClaudeComplianceCollector\bin\Collect-ClaudeCompliance.ps1' `
  -Mode Tail `
  -ConfigPath 'C:\ClaudeComplianceCollector\config\collector.config.json'

$LASTEXITCODE
```

初回未完了の状態でTailを指定すると、安全側に停止します。

### 終了コード

| コード | 意味                               |
| --- | -------------------------------- |
| `0` | 目標範囲の監査と本文照合が完了し、検出された本文gapが0    |
| `1` | API・認証・権限・JSON・I/O・整合性・再試行上限等で停止 |
| `2` | 照合は完了したが、取得不能・切り詰め等のgapあり        |
| `3` | 実行時間上限による未完了終了。再開可能              |
| `4` | 同じ保存先を使用する別処理が実行中のため未実行          |

`2`には、削除済み本文など、今回の要件で復元対象外とされているものが含まれる場合もあります。エラーとして無限に再試行するのではなく、対象IDと理由を確認します。

## 7. 全ページ取得・保存・checkpointの実装

### Activity Feed

初回は最新側の基点と、過去方向の進捗を分けています。

```text
初回の最新側基点：最初のページの first_id
過去方向の継続：last_id → after_id

Tailの開始位置：保存済みの確定 first_id → before_id
Tailの継続：各ページの first_id → before_id
```

Tailの確定位置は、`has_more=false`まで保存した後に更新します。途中のカーソルは別の作業状態として保持します。これは公式の前後方向のページ取得方式に合わせています。([Claude Platform][8])

反映遅延対策として、既定では上限を現在の120秒前に置き、前回上限の10分前から今回上限までを再照合します。公式は1分以上前の上限と、重複窓または過去窓の再照合を案内しています。10分を超える例外的な遅延まで保証するものではありません。([Claude Platform][8])

### 本文

チャット一覧とメッセージは`last_id → after_id`、プロジェクト一覧と添付一覧は`next_page → page`で、それぞれ最後まで取得します。本文のキュー・完了状態は監査とは別に保持します。([Claude Platform][1])

### 保存先

```text
C:\ClaudeComplianceCollector\
  data\raw\YYYY\MM\DD\<連番_GUID>\activities_YYYYMMDD.jsonl
  data\content\YYYY\MM\DD\<連番_GUID>\response.json
  data\reports\YYYY\MM\DD\<連番_GUID>\report.json
  state\checkpoint.json
  state\status.json
  logs\run_YYYYMMDD.txt
  logs\error_YYYYMMDD.txt
  staging\
```

日付は**取得時の日本時間**です。

提示された保存例から一段フォルダーを増やし、日付配下に保存単位ごとのJSONLを置いています。一つの日次ファイルへ追記する方式ではありません。保存途中の停止で、不完全な末尾を完成済みと扱わないためです。

保存順序は次のとおりです。

```text
stagingへデータとreceiptを書込み・Flush
    ↓
保存単位のフォルダーを公開
    ↓
checkpointを更新
```

起動時には保存済みreceiptと実ファイルの存在・ハッシュを検証します。保存後・checkpoint更新前に止まった場合は、以前の位置から読み直して重複を排除します。

監査は全日付を通じて`activity.id`で重複排除します。本文は同じIDだけでは除外せず、取得パスとrawレスポンスのSHA-256で同一保存物を判定します。更新後のレスポンスは別保存し、過去版を削除しません。

本文は受信したJSONバイト列を保存し、Activityもrawテキストから保存します。APIデータを`ConvertTo-Json`で再構成しないため、その変換による深さ制限・長文欠落を避けています。解析上限超過などの場合は、切り詰めて成功扱いせず停止します。

ただし、毎回全アーカイブを検証する設計なので、履歴が巨大になると起動時I/Oとメモリ使用量が増えます。ここも受入試験の計測対象です。

## 9. エラー処理と監視

通信エラー・タイムアウト・再試行対象の5xx・529等は同じ要求位置から再試行します。429は`retry-after`を優先し、`x-should-retry`の指示も反映します。ただし401／403は停止します。公式のエラー仕様を根拠にしています。([Claude Platform][10])

ログにはHTTPステータス、エラーtype、対象ID、request-id、試行回数、例外型、HResult等を記録します。**APIキー、認証ヘッダー、チャット本文、APIエラーメッセージ全文は出しません。** エラーメッセージ全文を出さないのは、本文や秘密が反映される危険を避けるためです。

監視では、特に次を分けます。

| 項目                           | 意味                        |
| ---------------------------- | ------------------------- |
| `activity.last_success_utc`  | 監査の対象窓を保存し終えた時刻           |
| `activity.last_window_upper` | 監査の確定取得上限                 |
| `body.last_sweep_utc`        | 本文照合が一巡した時刻。gapを含むことがある   |
| `body.last_sweep_cutoff_utc` | 本文照合の列挙上限                 |
| `body.last_sweep_gaps`       | 直近の本文取得制約数                |
| `last_no_gap_success_utc`    | 監査・本文が完了し、検出gapが0だった最後の時刻 |

独立した監視処理から、例えば1時間ごとに次を実行します。

```powershell
& 'C:\Program Files\PowerShell\7\pwsh.exe' -NoLogo -NoProfile -NonInteractive `
  -File 'C:\ClaudeComplianceCollector\bin\Check-ClaudeComplianceHealth.ps1' `
  -MaxAgeHours 36

$LASTEXITCODE
```

監視スクリプトの終了コードは、収集スクリプトとは別です。

| コード | 監視上の意味             |
| --- | ------------------ |
| `0` | 新しい完了記録あり          |
| `2` | 新しい完了記録はあるが既知gapあり |
| `3` | 古い・未完了等            |
| `1` | 状態を読めない、または壊れている   |

監査だけ成功して本文が止まっている場合や、古い本文照合が長期間かかっている場合も検知対象にしています。

**収集ホスト自体の停止も検知するには、監視を別ホストまたは外部の監視基盤に置いてください。** 同じPC内だけでは、そのPCが停止したときに通知できません。監視用アカウントにはstateの読取りだけを与え、本文やキーを公開する必要はありません。

## 10. 本番前に確認するテスト

詳細な手順と合格条件は、READMEの「本番前の受入試験」に収録しています。最低限、次を確認してください。

| テスト    | 確認内容                                                 |
| ------ | ---------------------------------------------------- |
| 複数ページ  | 検証環境で各PageSizeを1にし、監査・チャット・メッセージ・プロジェクト・添付が最後まで取得される |
| 途中停止   | 時間上限と強制停止の両方を試し、未保存位置から再開できる                         |
| 更新本文   | 同じチャット・プロジェクト・docを更新し、新版が保存され、旧版のハッシュが変わらない          |
| 日またぎ重複 | 翌日の再取得でも、全rawを通じた`activity.id`の重複が0                  |
| 取得制約   | 削除・404・切り詰めで、IDと理由が残り、本文成功扱いにならない                    |
| 排他・未起動 | Backfill中のTailが起動拒否され、タスク無効化・ホスト停止を外部監視が検知する         |

疑似429・401・403・529・再試行上限などはオフラインテストに含めています。本番APIへ故意に大量送信して429を発生させる試験は行わないでください。

ディスク不足や書込み拒否の試験も、**本番Cドライブではなく検証VM**で行います。

## 11. 取得できない条件・保持期間・バックアップ

収集前に削除された本文、保持期限を超えた本文、APIが提供しない過去の状態は復元しません。404だけで削除・不存在・別組織などを区別できない場合は、理由を断定せず記録します。([Claude Platform][1])

未確認事項として、READMEには次を明記しています。

* すべての本文・ツール入出力についての追加の最大長と例外条件は**不明**。
* 更新中のリソースを、全ページで完全に同一時点へ固定できる保証は**不明**。
* 列挙に現れないリソースや、通知なしにAPIが省略した内容の網羅的な検知は**保証できない**。
* 対象組織の実際の保持設定・API有効状態は、この実装では設定APIを読まないため**不明**。管理者による確認が必要。

Activity Feedは公式に6年間保持されますが、記録開始はCompliance API有効化後です。有効化前や無効化中の未記録イベントは後から取得できません。([Claude Platform][11])

本文は組織の保持方針や削除に依存します。Enterpriseのカスタム保持は最低30日で、通常データは設定しなければ無期限ですが、シークレットチャットは別に確認が必要です。また、保持期間を短く変更すると、範囲外のデータが直ちに削除される場合があります。([Claudeヘルプセンター][12])

**Cドライブ内だけではバックアップになりません。** `data`・`state`・`logs`・スクリプト・設定を、別ディスク／別ホスト等へ世代付きで保全してください。本文の重複排除では過去日付のpayloadを参照するため、古い日付フォルダーだけを削除・移動すると参照が壊れます。

バックアップと復元は、データとcheckpointが整合する一式で行います。ハッシュ検証は破損検知であり、物理ディスク障害への保護やWORM、電子署名の代わりではありません。
