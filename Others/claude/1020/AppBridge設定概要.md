## 最初に：添付スクリプト固有の注意点

**添付の収集スクリプトは、処理が完了しても終了コード「2」を返します。**  
そのため、単純に「終了コードが0以外なら通知」とすると、処理が完了した場合にもメールが送られてしまいます。

作成した追加スクリプトでは、今回実行した収集プロセスについて、次の両方を満たした場合を「処理完了」と判定します。

1. 終了コードが `2`
2. 最後に次の完了メッセージが出力されている

```text
ClaudeComplianceCollector exit=2; processCompleted=True; see protected logs/state.
```

この判定は、添付された Collect-ClaudeCompliance(3)(1).ps1 の終了処理に合わせています。

動作は次のとおりです。

| 収集結果 | 追加スクリプトの動作 |
|---|---|
| 処理が完了した | 通知しない |
| 途中でエラーになったが、内部の再試行で回復し、処理が完了した | 通知しない |
| 再試行しても回復せず、最終的に失敗した | App Bridgeの通知コマンドを1回実行 |
| 元スクリプトを起動できない、正常完了を確認できない | App Bridgeの通知コマンドを1回実行 |
| 通知コマンド自体が失敗した | 再送せず、追加ログと終了コードで分かるようにする |

なお、ここでいう「処理完了」は元スクリプトが最後まで処理を終えたという意味です。元スクリプトが許容している取得不能データや、APIの網羅性の制約まで通知対象にするものではありません。

## 1．Windows側で、通知コマンドの場所を確認する

今回使用するのは、Windows Agentに同梱されている **`SendErrorEx`** です。件名・本文・専用の通知コードを指定できます。

Windows Agentの実際のインストールフォルダーを開き、次のファイルを確認してください。

```text
Windows Agentのインストールフォルダー\CLI\SendErrorEx.exe
```

添付資料では、Windows版の送信コマンドはインストールフォルダー配下の `CLI` にあるとされています。**製品の既定インストール先のフルパスは記載されていないため、実際の場所を確認してください。**

場所が分からない場合は、Windowsの「サービス」でApp Bridge MonitorのAgentサービスのプロパティを開き、「実行ファイルのパス」を手がかりにインストールフォルダーを確認できます。

根拠は 011900_070_App_Bridge_Monitor_UserMessage.pdf の印刷p.3、pp.8–9です。PDFのページ順ではp.6、pp.11–12に該当します。

## 2．App Bridgeにメール通知先を登録する

### 2-1．「標準通知先」を追加する

App BridgeのWeb画面で **「標準通知先」→「追加」** を開き、以下を入力します。

| 項目 | 設定例 |
|---|---|
| 標準通知先コード | `CLAUDE_COMPLIANCE_MAIL` |
| 標準通知先名 | `Claude収集エラーメール` |
| 有効にする | チェックする |

「OK」で保存します。

### 2-2．受信したいメールアドレスを追加する

作成した標準通知先の詳細を開き、**「指定アドレスを通知先に追加」** を押します。

| 項目 | 設定値 |
|---|---|
| 通知先アドレス | エラーを受信するメールアドレス |
| 種別 | `To` |
| 有効にする | チェックする |

「OK」で保存してください。同じメールアドレスを、この通知先に重複登録しないようにします。

この方法は資料中の「オンデマンド通知先」に該当し、宛先用のApp Bridgeユーザーを新規登録せずに設定できます。

また、**オーナ基本設定と対象ノード基本設定の両方**で、次が有効になっていることを確認してください。

- 「通知メッセージを有効にする」
- 「標準通知を行う」

既に有効なら、そのままで構いません。

このメール通知先の設定と、次の通知振分条件の設定は、011902_100_App_Bridge_Notification (1).pdf の印刷pp.2–10、pp.35–38に基づいています。

## 3．専用の「通知振分条件」を追加する

今回の通知だけをメールへ振り分けるため、**`91CC-001-E`** という専用の通知コードを使用します。作成した追加スクリプトにも、このコードを設定済みです。

Web画面で **「通知振分条件」→「追加」** を開き、以下を設定してください。

| 項目 | 設定値 |
|---|---|
| 順序番号 | 例：`10`。今回の通知に一致する既存条件より先になる番号 |
| 通知振分条件コード | `CLAUDE_COMPLIANCE_ERROR` |
| 通知振分条件名 | `Claude収集の最終失敗` |
| 有効にする | チェックする |
| 利用開始日時 | 現在以前の日時 |
| 利用終了日時 | 通常は「設定する」を外す |
| **後続振分条件の評価** | **チェックを外す** |
| **メッセージの種類と発生理由** | **「設定する」→「発生理由を指定する」→「メッセージ受信」** |
| **メッセージ種類** | **Errorだけチェックする** |
| **通知コードを比較する正規表現** | 「設定する」をチェックし、 **`^91CC-001-E$`** |
| ノードCD・ノードタグの条件 | 今回専用の通知コードを使うなら未設定で可 |
| 件名・本文の正規表現 | 未設定 |
| 指定日・休日属性・曜日指定・指定時刻 | 常時通知したい場合は未設定 |
| 標準通知先 | `CLAUDE_COMPLIANCE_MAIL` |
| 電話通知先 | 選択しない |

「OK」で保存します。

**特に間違えやすいのは、発生理由です。今回は「メッセージ受信」を選びます。** `SendErrorEx` から送ったユーザメッセージを受け取る条件になります。

### 重複メールを防ぐための設定

通知振分条件は、順序番号の小さい順に評価されます。

今回の条件を、**今回の通知に一致するすべての既存条件より先**に配置し、「後続振分条件の評価」を外してください。

初期状態の `_DEFAULT` は順序番号9999ですが、ほかに先行する汎用条件があれば、その条件より先にする必要があります。後続評価を外しても、それより前の条件で既に送られたメールは取り消せません。

`91CC-001-E` が既に別用途で使われている場合は、別の未使用コードを選び、スクリプト側とWeb側の両方を同じ値に変更してください。

## 4．追加スクリプトをWindowsに配置する

ダウンロードした追加スクリプトを、例として次の場所に保存してください。

```text
C:\ClaudeComplianceCollector\Invoke-ClaudeComplianceWithAppBridge.ps1
```

元の収集スクリプトは、現在使っている名前・場所のままで構いません。

追加スクリプトをテキストエディターで開き、**冒頭の3つのパス**を実環境に合わせて変更します。

```powershell
[string]$CollectorPath = 'C:\ClaudeComplianceCollector\Collect-ClaudeCompliance(3)(1).ps1',
[string]$ConfigPath = 'C:\ClaudeComplianceCollector\config.json',
[string]$SendErrorExPath = 'C:\REPLACE_WITH_AGENT_INSTALL_FOLDER\CLI\SendErrorEx.exe',
```

| 設定項目 | 指定するもの |
|---|---|
| `CollectorPath` | 現在使用している元の収集スクリプト |
| `ConfigPath` | 現在使用しているconfig.json |
| `SendErrorExPath` | 手順1で確認したSendErrorEx.exe |

**`REPLACE_WITH_AGENT_INSTALL_FOLDER` は仮文字列なので、必ず置き換えてください。**

元スクリプトの名前が `Collect-ClaudeCompliance.ps1` なら、`CollectorPath` にその名前を指定します。引用符と行末のカンマは残し、UTF-8で保存してください。

追加スクリプトの実行ログは、既定で次に保存されます。

```text
C:\ClaudeComplianceCollector\logs\AppBridgeWrapper\
```

### 実行ユーザーとPowerShellについて

元の収集スクリプトは、**PowerShell 7.4以上・64ビットのWindowsプロセス**を要求しています。起動には `pwsh.exe` を使います。

また、**タスクの実行ユーザーは現在と同じにしてください。** 元スクリプトは実行ユーザーの環境変数からAPIキーを取得するため、ユーザーを変えるとキーが見えなくなる場合があります。追加スクリプトへのAPIキーの記入は不要です。

## 5．収集を動かさずに、テストメールを送る

Web側の設定とパスの変更が済んだら、タスクと同じ実行ユーザーで、次をPowerShellから実行します。

```powershell
& 'C:\Program Files\PowerShell\7\pwsh.exe' -NoLogo -NoProfile -NonInteractive -File 'C:\ClaudeComplianceCollector\Invoke-ClaudeComplianceWithAppBridge.ps1' -TestNotification
$LASTEXITCODE
```

`pwsh.exe` のインストール先が異なる場合は、そのパスに置き換えてください。

**このテストでは元の収集スクリプトを実行せず、実際のテスト通知を1回送ります。** APIキーやconfigを故意に壊してエラーを発生させる必要はありません。

次の3点を確認してください。

1. 表示される終了コードが `0`
2. App Bridgeに、通知コード `91CC-001-E` のテストメッセージが1件記録される
3. 指定したメールアドレスに、件名に `[TEST]` を含むメールが1通届く

**終了コード0は「通知コマンドが正常終了した」という意味で、メール到着の保証ではありません。** Agent経由で送られるため、実際の受信まで確認してください。

タスク用ユーザーで対話ログオンできない場合は、次の手順のタスク引数に一時的に `-TestNotification` を追加して、タスクからテストできます。確認後は必ずこの引数を削除します。

## 6．タスクスケジューラの起動先を変更する

既存タスクの **「プロパティ」→「操作」** を開き、元の収集スクリプトを起動している操作を編集します。

### 「操作」の設定

| 項目 | 設定例 |
|---|---|
| 操作 | プログラムの開始 |
| プログラム／スクリプト | `C:\Program Files\PowerShell\7\pwsh.exe` |
| 引数の追加 | `-NoLogo -NoProfile -NonInteractive -File "C:\ClaudeComplianceCollector\Invoke-ClaudeComplianceWithAppBridge.ps1"` |
| 開始（オプション） | `C:\ClaudeComplianceCollector` |

「開始」にはフォルダーパスを入れ、引用符は付けません。

**収集を起動する既存の操作を、追加スクリプトへの起動に置き換えてください。** 追加スクリプトが内部で元スクリプトを実行するため、元の起動操作を別に残すと二重実行になります。

現在の実行ユーザー、トリガー、実行時刻、必要な環境変数の準備は引き継いでください。実行権限・スクリプト署名・実行ポリシーも現在の運用に合わせます。

### 「設定」タブ

| 項目 | 今回の設定 |
|---|---|
| タスクが失敗した場合の再起動の間隔 | **チェックを外す** |
| タスクが既に実行中の場合に適用される規則 | **新しいインスタンスを開始しない** |

元の収集スクリプト内の再試行は、そのまま動きます。一方、タスクスケジューラの「失敗時の再起動」は収集全体の別実行になるため、失敗するたびにまた通知されます。今回の運用ではタスク側の再起動を無効にします。多重起動も、新しい実行を開始しない設定にします。[Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-restartonfailure-settingstype-element?utm_source=chatgpt.com)

また、タスクの実行時間制限が短すぎると、再試行中に追加スクリプトごと停止され、通知まで到達できません。初回取得や再試行を含む所要時間を考慮してください。

## 7．変更後のタスクを1回実行して確認する

本番用の引数から **`-TestNotification` が外れていること**を確認し、既存タスクを右クリックして「実行」します。この操作では実際の収集を行うため、現在の収集が終わっているタイミングで実施してください。

正常に処理が完了した場合の期待結果は、次のとおりです。

- タスクの「前回の実行結果」が `0x0`
- メールは送られない
- 追加ログに `COLLECTOR exit=2; completed=True` がある
- 追加ログに `notificationAttempted=False` がある

追加スクリプトが返す終了コードは、次のように整理しています。

| タスクの実行結果 | 意味 |
|---|---|
| `0x0` | 収集処理が完了。テストモードの場合は通知コマンド成功 |
| `0x1` | 収集・起動・完了確認で失敗し、通知コマンドは正常終了 |
| `0xA`（10） | 通知コマンドの起動・実行にも失敗。追加ログを確認 |

実際のエラー通知では、件名に `[ERROR] Claude コンプライアンスログ収集 最終失敗` を設定し、本文にホスト名、実行ID、開始・終了時刻、収集側の終了コード、ログの場所などを含めます。

## メールが届かない場合の確認先

| 状況 | 主な確認先 |
|---|---|
| テストが終了コード10になる | `SendErrorExPath`、実行ユーザーの権限、追加ログの `NOTIFY_RESULT`／`NOTIFY_FAILURE` |
| 通知コマンドは成功したが、App Bridgeに表示されない | Agentの稼働・センタ通信、対象ノード、通知メッセージの有効設定、抑止条件 |
| App Bridgeには表示されるが、メールが届かない | オーナ／ノードの「標準通知を行う」、通知先の有効状態、振分の「メッセージ受信・Error・専用コード」、迷惑メール |
| メールが複数届く | 先行する汎用振分条件、後続条件の評価、宛先の重複、タスクの再起動・二重起動 |

作成した追加スクリプトは、PowerShell 7.6.6のLinux環境で模擬コマンドを使って20ケースを確認し、**回復後の完了では通知0回、最終失敗では通知1回、通知コマンドが失敗しても再送しない**ことを確認しています。Windows上の実際のAgent受付とメール到着は、上記のテストで確認してください。

なお、この方式で通知できるのは追加スクリプトが動作している場合です。Windows停止、タスク未起動、追加スクリプト自体の強制終了は、必要に応じて別の死活・実行監視で補います。
