# Claudeコンプライアンスログ収集の最終失敗をApp Bridgeからメール通知する手順

対象：Windows、App Bridge Monitor Windows Agent導入済み、タスクスケジューラで収集中。

元の収集スクリプトは変更しません。追加する `Invoke-ClaudeComplianceWithAppBridge.ps1` が元のスクリプトを別のPowerShellプロセスで実行し、最終結果を確認して、失敗時だけ `SendErrorEx` を1回呼び出します。メールの宛先はApp BridgeのWeb画面で設定します。

## 1. 今回の判定方針

**添付された収集スクリプトは、処理が完了した場合にも終了コード2を返します。0以外をすべて失敗とする判定は使いません。**

今回実行した子プロセスについて、次の両方を満たす場合に処理完了とします。

1. 実際のプロセス終了コードが `2`。
2. 次の行が1回出力され、最後の空行でない出力行になっている。

```text
ClaudeComplianceCollector exit=2; processCompleted=True; see protected logs/state.
```

| 元の収集結果 | 通知 | タスクに返す値 |
|---|---|---|
| 終了コード2＋上記完了行 | なし | 0 |
| 途中でエラーがあったが、内部リトライで回復し、最後に上記条件を満たす | なし | 0 |
| 最終失敗：終了コード1・3・4・5・6など | SendErrorExを1回呼び出す | 通知コマンド成功なら1 |
| 起動できない、完了行がない、想定外の終了コード0など | SendErrorExを1回呼び出す | 通知コマンド成功なら1 |
| 通知コマンド自体の起動・実行に失敗 | 再送は行わず、ローカルログに記録 | 10 |

`error_*.txt` の存在、エラーログの行数、`counts.errors` は判定に使いません。元のスクリプトは途中の失敗を記録してからリトライするためです。共有の `state\status.json` も判定には使いません。起動直後の失敗などで以前の実行結果が残る場合や、status保存後に最終ログ出力が失敗する場合があるためです。

この方針の「処理完了」は、元のスクリプトが処理を最後まで終えたことを指します。元スクリプトが許容するデータ取得不能やAPIの網羅性の制限まで、エラーとして通知するものではありません。

## 2. 作業前に控える内容

現在のタスクを開き、次を控えてください。必要であればタスクの右クリック→「エクスポート」で設定を保存します。

| 確認するもの | 用途 |
|---|---|
| 元の収集スクリプトの絶対パス | 追加スクリプトの `CollectorPath` に設定 |
| 現在利用中のconfig.jsonの絶対パス | `ConfigPath` に設定 |
| タスクを実行しているWindowsユーザー | 変更後も同じユーザーを使用 |
| 既存タスクのトリガー、実行時刻、必要な環境設定 | 変更後も引き継ぐ |
| Windows Agentのインストールフォルダー | `CLI\SendErrorEx.exe` の場所を確認 |

元スクリプトはPowerShell **7.4以上・64ビットのWindowsプロセス**を要求しています。起動プログラムには `pwsh.exe` を使用してください。通常の例は `C:\Program Files\PowerShell\7\pwsh.exe` です。実際に使用中のパスに合わせてください。

元スクリプトは、実行ユーザーのユーザー環境変数 `CLAUDE_COMPLIANCE_ACCESS_KEY` を優先し、次にプロセス環境変数を参照します。ユーザーを変更するとキーが見えなくなる場合があります。追加スクリプトにAPIキーを書き込む必要はありません。現在のタスクで環境変数を準備する処理がある場合は、その準備も引き継いでください。

## 3. SendErrorEx.exeの場所を確認する

Windows Agentの実際のインストールフォルダーを開き、その中の `CLI` フォルダーで `SendErrorEx.exe` を確認します。

```text
Windows Agentのインストールフォルダー\CLI\SendErrorEx.exe
```

添付資料にはインストール先の固定フルパスは記載されていません。場所が分からなければ、Windowsの「サービス」でApp Bridge MonitorのAgentサービスのプロパティを開き、「実行ファイルのパス」を手がかりにインストールフォルダーを確認してください。通知用に設定するのは、サービス実行ファイルではなく、そのフォルダー配下の `CLI\SendErrorEx.exe` です。

このコマンドはWindows Agentに同梱されるため、今回の方法のために別の連携ツールやAPIトークンを追加する必要はありません。通知はAgent経由でApp Bridgeセンタへ送られます。

## 4. App Bridgeにメール通知先を追加する

### 4-1. 標準通知先を作る

App BridgeのWeb画面で「標準通知先」を開き、「追加」を押します。

| 項目 | 設定例 |
|---|---|
| 標準通知先コード | `CLAUDE_COMPLIANCE_MAIL` |
| 標準通知先名 | `Claude収集エラーメール` |
| 有効にする | チェック |

「OK」で保存します。

### 4-2. 受信用メールアドレスを登録する

作成した標準通知先の詳細を開き、「指定アドレスを通知先に追加」を押します。

| 項目 | 設定値 |
|---|---|
| 通知先アドレス | エラーを受信するメールアドレス |
| 種別 | `To` |
| 有効にする | チェック |

「OK」で保存します。この方式は「オンデマンド通知先」です。App Bridgeのユーザー登録を追加せずに宛先を設定できます。同じアドレスをこの通知先に重複登録しないでください。

オーナ基本設定と対象ノード基本設定の「通知メッセージを有効にする」「標準通知を行う」も有効であることを確認してください。既に有効なら追加変更は不要です。これらが無効で変更権限がない場合は、その設定を変更できる管理者に有効化を依頼してください。

## 5. 専用の通知振分条件を追加する

「通知振分条件」画面で「追加」を押し、以下を設定します。

| 項目 | 設定値 |
|---|---|
| 順序番号 | 例：`10`。今回の通知に一致する既存の条件より先になる番号 |
| 通知振分条件コード | `CLAUDE_COMPLIANCE_ERROR` |
| 通知振分条件名 | `Claude収集の最終失敗` |
| 有効にする | チェック |
| 利用開始日時 | 現在以前の日時 |
| 利用終了日時 | 通常は「設定する」を外す |
| 後続振分条件の評価 | **チェックを外す** |
| メッセージの種類と発生理由 | **「設定する」→「発生理由を指定する」→「メッセージ受信」** |
| メッセージ種類 | **Errorだけチェック** |
| 通知コードを比較する正規表現 | 「設定する」をチェックし、 **`^91CC-001-E$`** |
| ノードCDを比較する正規表現 | 今回専用の通知コードを使うなら未設定で可 |
| ノードタグ、件名・本文の正規表現 | 未設定 |
| 指定日、休日属性、曜日指定、指定時刻 | 常時メールを受ける場合は未設定 |
| 標準通知先 | `CLAUDE_COMPLIANCE_MAIL` |
| 電話通知先 | 選択しない |

「OK」で保存します。

**発生理由は「メッセージ受信」です。** `SendErrorEx` で送ったユーザメッセージを受け取る条件です。

`91CC-001-E` はこの手順で選んだ専用コードです。製品の固定コードではありません。既に別用途で使っている場合は有効な形式の未使用コードを選び、追加スクリプトの `$notificationCode` とWebの正規表現を両方変更してください。形式は `ZZXX-XXX-X`、`ZZ` は91～95、`X` は英字または数字です。

### 重複を防ぐために確認すること

通知振分条件は順序番号の小さい順に評価されます。初期状態の `_DEFAULT` は9999ですが、それより前に別の汎用条件がある場合もあります。

今回の条件を、**今回のメッセージに一致するすべての既存条件より先**に置き、「後続振分条件の評価」を外してください。これにより今回の条件が一致した後の通知を止めます。先に別の条件で送信済みのメールを取り消す機能ではありません。同じ順序番号の条件を作らず、必要に応じて既存条件の番号を調整してください。

ノードをさらに絞りたい場合は、App Bridgeに表示される実際のノードCDを使って完全一致の正規表現を設定します。ノードCDが必ずWindowsのコンピューター名と同じとは限りません。例えばノードCDが `SERVER01` なら `^SERVER01$` です。ピリオドなど正規表現の特殊文字を含む場合はエスケープが必要です。

## 6. 追加スクリプトを配置・設定する

例として、追加スクリプトを次の場所に保存します。

```text
C:\ClaudeComplianceCollector\Invoke-ClaudeComplianceWithAppBridge.ps1
```

元の収集スクリプトは、現在使用している場所・名前のままで構いません。追加スクリプトをテキストエディターで開き、冒頭の3つのパスを実環境に合わせます。

```powershell
[string]$CollectorPath = 'C:\ClaudeComplianceCollector\Collect-ClaudeCompliance(3)(1).ps1',
[string]$ConfigPath = 'C:\ClaudeComplianceCollector\config.json',
[string]$SendErrorExPath = 'C:\REPLACE_WITH_AGENT_INSTALL_FOLDER\CLI\SendErrorEx.exe',
```

`REPLACE_WITH_AGENT_INSTALL_FOLDER` は置き換え必須の仮文字列です。手順3で確認した実際のインストール先に変更してください。引用符と行末のカンマを残し、文字コードはUTF-8で保存します。CollectorPathのファイル名は例です。現在のファイル名が `Collect-ClaudeCompliance.ps1` なら、その名前を指定します。

追加スクリプトの実行記録は、既定で以下に作られます。

```text
C:\ClaudeComplianceCollector\logs\AppBridgeWrapper\wrapper_日時_実行ID.log
```

実行ユーザーには、追加・元スクリプトとconfigの読み取り、通知コマンドの実行、ログフォルダーへの書き込みが必要です。ファイルへのアクセス権は現在の収集用フォルダーの運用に合わせてください。

## 7. 収集を動かさずに通知経路をテストする

タスクと同じ実行ユーザーで、次をPowerShellから実行します。`pwsh.exe` の場所が異なる場合は置き換えてください。

```powershell
& 'C:\Program Files\PowerShell\7\pwsh.exe' -NoLogo -NoProfile -NonInteractive -File 'C:\ClaudeComplianceCollector\Invoke-ClaudeComplianceWithAppBridge.ps1' -TestNotification
$LASTEXITCODE
```

このテストでは**元の収集スクリプトは実行せず、実際のテスト通知を1回送ります。** APIキー・config・収集済みデータの変更は不要です。

確認する結果は次の3点です。

1. 終了コードが `0`。これは通知コマンドが正常終了した意味です。
2. App Bridgeに、通知コード `91CC-001-E`、種類Error、発生理由「メッセージ受信」のテストメッセージが1件記録される。
3. 指定した宛先に、件名に `[TEST]` を含むメールが1通届く。

SendErrorExが0で終了しても、Agentからの送信やメール配送が完了した証明にはなりません。Agent経由のため遅延する場合があります。実際のメール受信まで確認してください。

タスク用ユーザーで対話ログオンできない場合は、手順8のタスク操作の引数に一時的に `-TestNotification` を付けて、タスクの「実行」から同じ確認を行えます。テスト後は必ずその引数を削除し、本番用の引数に戻してください。

## 8. タスクスケジューラの起動先を変更する

既存タスクの「プロパティ」→「操作」で、収集スクリプトを起動している操作を編集します。

| 項目 | 設定例 |
|---|---|
| 操作 | プログラムの開始 |
| プログラム／スクリプト | `C:\Program Files\PowerShell\7\pwsh.exe` |
| 引数の追加 | `-NoLogo -NoProfile -NonInteractive -File "C:\ClaudeComplianceCollector\Invoke-ClaudeComplianceWithAppBridge.ps1"` |
| 開始（オプション） | `C:\ClaudeComplianceCollector` |

「開始」にはフォルダーパスを指定し、引用符は付けません。プログラム欄には実行ファイルのパスだけを指定し、`-File` などを入れません。

収集を起動する既存の操作を、この追加スクリプトへの起動に置き換えます。追加スクリプトが内部で元のスクリプトを呼ぶので、元の起動操作を別に残すと二重実行になります。現在の実行ユーザー、トリガー、実行時刻、必要な環境準備は引き継いでください。「最上位の特権で実行する」やログオン条件も、現在の動作中の設定に合わせます。スクリプト署名・実行ポリシーも、現在の運用に合わせて適用してください。

### 「設定」タブ

| 項目 | 今回の設定 |
|---|---|
| タスクが失敗した場合の再起動の間隔 | **チェックを外す** |
| タスクが既に実行中の場合に適用される規則 | **新しいインスタンスを開始しない** |

元の収集スクリプト内のリトライは、そのまま動きます。タスクスケジューラの再起動は収集全体の別実行になるため、失敗するたびにまた通知されます。今回の1回の予定実行につき最終失敗を1回通知する運用では、タスク側の再起動を無効にします。

「タスクを停止するまでの時間」を短く設定している場合も確認してください。リトライや初回取得の途中で追加スクリプトごと強制停止されると、通知処理まで到達できません。通知まで実行する必要がある場合は、通常の最大所要時間とリトライを考慮した設定にしてください。

## 9. 本番と同じタスクから1回実行して確認する

本番引数から `-TestNotification` が外れていることを確認し、既存タスクを右クリック→「実行」します。この操作では実際の収集処理が実行されるため、現在の収集が終わっているタイミングで行います。

処理完了時の期待結果：

- タスクの「前回の実行結果」が `0x0`。
- メールは送られない。
- 追加ログに `COLLECTOR exit=2; completed=True` と `notificationAttempted=False` がある。

最終失敗時は次のようになります。

| 前回の実行結果 | 意味 |
|---|---|
| `0x0` | 収集処理が完了。テストモードでは通知コマンド成功 |
| `0x1` | 収集・起動・完了確認で失敗し、SendErrorExは0で終了 |
| `0xA`（10） | 通知コマンドの起動・実行にも失敗。追加ログを確認 |

これは追加スクリプトが返す終了コードです。実行ファイルが起動しない、タスクのログオンに失敗する等の場合は、タスクスケジューラが別のエラーを表示します。

実エラー時の件名は `[ERROR] Claude コンプライアンスログ収集 最終失敗` です。本文には、ホスト、App BridgeノードCD、追加スクリプトの実行ID、開始・終了時刻、収集側終了コード、固定の失敗分類、ログの場所を含めます。APIキー・APIレスポンス本文・収集ログ全文はメールへ載せません。

元の収集側終了コードの目安：

| コード | 添付スクリプトでの主な意味 |
|---|---|
| 1 | リトライ上限到達、その他API／JSON／入出力エラー、最終ログ保存失敗など |
| 2 | 処理完了。APIの網羅性には制約が残る |
| 3 | 認証・権限、関連する不正なパス等 |
| 4 | チェックポイント／整合性／復旧に関する問題 |
| 5 | 設定・キー・実行環境等の問題 |
| 6 | 別の収集プロセスがロックを保持している |

詳細は `C:\ClaudeComplianceCollector\logs` の該当時刻の `run_*.txt`、対応する `error_*.txt` と追加ログを確認してください。追加スクリプトのRunIdと元の収集スクリプトのrunIdは別です。時刻と元ログのSTART／ENDを照合してください。`status.json` は最新の実行で更新できているか確認してから参照します。

## 10. テストメールが届かない場合

| 状況 | 確認する内容 |
|---|---|
| テスト終了コード10 | 追加ログの `NOTIFY_RESULT`／`NOTIFY_FAILURE`、SendErrorExの実際のパス、実行ユーザーの権限 |
| SendErrorExの戻り値12 | 引数が正しいか。専用コード、件名・本文を確認 |
| SendErrorExの戻り値16 | コマンド例外。追加ログの標準エラー出力とAgent状態を確認 |
| SendErrorExの戻り値20 | 同一コマンド種の1時間当たり実行回数制限 |
| 通知コマンドは0だがApp Bridgeに表示されない | Agentの稼働、センタへの通信、対象ノード、通知メッセージの有効設定、抑止条件 |
| App Bridgeには表示されるがメールが来ない | オーナ／ノードの「標準通知を行う」、標準通知先とアドレスの有効状態、振分の種類・理由・コード・順序・利用開始日時、迷惑メール |
| 確認状態が「抑止」 | 通知抑止条件に一致している。抑止されたメッセージは通常の通知振分対象にならない |
| メールが複数届く | 先行の汎用振分、後続評価、宛先重複、タスク再起動、別タスクの重複起動を確認 |

App Bridgeのコマンドは通常、同一コンピューターの同一コマンド種で100回／時の制限があります。ノードレベルでは、同じサーバインスタンス・メッセージ種類・通知コードのユーザメッセージに同一分内10件の書き込み制限があるため、短時間に何度もテストせず、1回ずつ結果を確認してください。

## 11. この方式の範囲

追加スクリプトが動作し、子プロセスの終了を受け取れることが前提です。Windows停止、タスク未起動、追加スクリプト自体の構文エラーや強制終了、終了しない収集プロセスは、この方式だけでは検知・通知できません。必要なら別途、Agentの死活監視や未実行／長時間実行の監視で補います。

保証する回数は、追加スクリプトが1実行につきSendErrorExを最大1回呼び出すことです。CLIの成功はメール到着の保証ではありません。センタ通信の再試行はAgent側に任せ、追加スクリプトから同じ通知を繰り返し送信しない設計です。

元の収集スクリプトの終了コードや最後の完了行を将来変更した場合は、この追加スクリプトの完了判定も確認してください。
