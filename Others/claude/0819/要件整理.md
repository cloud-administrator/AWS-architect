# 特に修正した方がよい4項目

### 1. 「必ずユーザー承認」は定義を変えることを推奨

現在の文言だと、

> ファイルを1個読むだけでも毎回承認する

という意味になります。

Claude CodeのManual modeでは、Workspace内のRead/Grepは通常承認されません。また、一部のread-only shell commandも承認不要です。 ([Claude][2])

企業用途なら、次の要件の方が現実的です。

> **ファイル変更、ファイル作成・削除、PowerShell等のコマンド実行、Webアクセス、MCP等の外部アクセスについては自動承認を禁止し、ユーザー承認を必須とする。ファイル読み取りについては、許可された `claude_work` 配下に限り承認不要とする。Auto modeおよびPermission bypassは禁止する。**

これを推奨します。

`permissions.disableBypassPermissionsMode` と `permissions.disableAutoMode` でAuto/bypassを禁止でき、`allowManagedPermissionRulesOnly` によりUser/Project側のpermission rule追加も止められます。 ([Claude][1])

---

# 2. 「Web検索はキャッシュのみ」は変更が必要

これは**実現不可**と考えてください。

公式仕様には、

* `WebSearch`：Web検索
* `WebFetch`：URL取得
* WebFetch結果はデフォルト15分Cache
* Cache TTLは変更可能

まではありますが、

> Cache Hit → 使用
> Cache Miss → 外部通信禁止

というCache-only機能はありません。 ([Claude][3])

したがって企業要件としては、次のどちらかに変更する必要があります。

**セキュリティ優先なら推奨はAです。**

**A. Webアクセスそのものを禁止する**

> WebSearchおよびWebFetchによるインターネットアクセスは禁止する。また、PowerShell等による外部Webアクセスについても禁止する。

または、

**B. Webアクセス先をallowlist方式にする**

> Webアクセスは管理者が許可したDomainに限定し、それ以外は禁止する。

「Cache-only」は要件から削除することを推奨します。

---

# 3. `claude_work` だけのWorkspace制限

ここが今回最も難しい部分です。

Claude Codeには `/cd` のallowlist機能があり、

> `~/claude_work` とその配下だけ `/cd` 可能

という制御自体はできます。 ([Claude][2])

しかし、

> **Claude Codeそのものを `claude_work` 以外から起動できなくする**

というManaged settingsは、現在の公式仕様には確認できません。

さらにNative WindowsではSandboxが使えません。Anthropic公式では明確に、

> SandboxはmacOS、Linux、WSL2対応。Native Windowsは非対応

となっています。 ([Claude][6])

したがって、今回の前提を

> **Native Windows ＋ Managed settingsだけ**

に固定するなら、

**「`claude_work` 以外へ絶対にアクセスできない」ことを強固なセキュリティ境界として保証するのは困難**

です。

Claude CodeのRead/Edit permissionはbuilt-in Toolには効きますが、PythonやNode等の任意の子プロセスによるファイルアクセスには完全には適用されず、AnthropicもOSレベルの強制にはSandboxを使うよう説明しています。 ([Claude][2])

### そのため要件文は

> **Claude Codeからのファイル読み取り・編集・作成・削除は、原則として `%USERPROFILE%\claude_work` 配下に限定する。`/cd` による作業Directory変更も同配下に限定する。Claude CodeのPermission機構で制御可能な範囲において、同Directory外へのアクセスを禁止する。**

とした方が仕様上正確です。

「絶対にアクセスできない」と書くと、Native Windows＋settings.jsonのみという前提と矛盾します。

---

# 4. Windows共有フォルダ禁止も「絶対禁止」は注意

Claude CodeはWindowsの

```text
\\server\share\file
```

のようなUNC pathを認識し、Windows Credentialが相手Hostへ送信される可能性があるため、Command中にUNC pathが含まれる場合はPermission promptを出す設計になっています。 ([Claude][1])

ただし、

* UNC path
* `Z:` 等にMapされたNetwork drive
* PowerShell script内部からアクセス
* Python/Node等からアクセス

をすべて一つのWildcardで完全に検出・禁止する仕様は、今回確認した公式ドキュメントにはありません。

したがって、

> **Claude CodeのPermission機構で検出可能なUNC pathおよびNetwork resourceへのRead/Writeを禁止する。Mapped network driveを含めたOSレベルの完全なNetwork folder禁止は本settings.jsonの保証範囲外とする。**

という要件にするのが正確です。

# 追加した方がよい企業向け要件

現在の要件には、以下を追加することを強く推奨します。

| 追加要件                             | 重要度 | 理由                                                       |
| -------------------------------- | --: | -------------------------------------------------------- |
| **Auto mode禁止**                  | ★★★ | ユーザー承認必須要件と整合させる                                         |
| **bypassPermissions禁止**          | ★★★ | `--dangerously-skip-permissions` 等による承認迂回を禁止する           |
| **Permission ruleをManaged限定**    | ★★★ | User/Project側でallow ruleを追加させない                          |
| **Managed settings取得失敗時は起動禁止**   | ★★★ | `forceRemoteSettingsRefresh`。初回取得失敗時などにPolicyなしで起動するのを防ぐ |
| **Claude Code最低Versionを固定**      | ★★★ | 古いClaude CodeでPolicyが効かないことを防ぐ                           |
| **必要なら最大Versionも固定**             | ★★☆ | 社内検証前の新版利用を防ぐ                                            |
| **企業OrganizationへのLogin固定**      | ★★★ | 個人Claude Organizationでの利用を防止                             |
| **MCP sideload禁止**               | ★★★ | `--mcp-config` 等から管理外MCPを持ち込ませない                         |
| **Plugin Marketplace制限**         | ★★★ | 管理外PluginからSkill/MCP等を持ち込ませない                            |
| **SkillによるShell実行禁止**            | ★★☆ | Skill経由のCommand executionを抑止                             |
| **Claude.ai Connectors利用可否を決める** | ★★★ | MCPを管理者管理にするなら整合を取る                                      |
| **Remote Control利用可否を決める**       | ★★☆ | 外部端末からSession操作を許可するか決定                                  |
| **Artifact公開利用可否を決める**           | ★★☆ | Session outputのWeb公開機能を許可するか決定                           |

これらはManaged settingsから制御できます。特に `forceRemoteSettingsRefresh` は、server-managed settingsが取得できなかった際にPolicyなしで起動することを防ぐ**fail-closed**設定なので、今回のようなセキュリティ重視要件では重要です。 ([Claude][5])

# 私なら要件をこう整理します

次回settings.jsonを作成する前提として、要件を以下の形に修正することを推奨します。

1. **作業領域**
   `%USERPROFILE%\claude_work` をClaude Codeの標準作業領域とし、Claude CodeのPermission機構で制御可能な範囲では同Directoryとその配下だけファイルアクセスを許可する。

2. **Workspace移動**
   `/cd` による移動先は `%USERPROFILE%\claude_work` とその配下に限定する。 ([Claude][2])

3. **ファイル操作**
   `claude_work` 外へのRead/Edit/Writeを禁止する。Symlink等を利用したWorkspace外へのアクセスも禁止対象とする。Claude CodeはRead/Edit rule評価時にsymlink先も確認します。 ([Claude][2])

4. **ユーザー承認**
   ファイル変更、PowerShell/Command実行、Webアクセス、MCP等の外部アクセスは原則ユーザー承認を必須とする。Workspace内の通常のファイルReadは承認不要とする。

5. **Permission bypass禁止**
   Auto modeおよびbypassPermissionsを禁止し、Permission ruleはManaged settingsからのみ定義可能とする。 ([Claude][1])

6. **Windows Network resource**
   UNC path等のNetwork resourceへのアクセスを禁止する。ただしNative Windows＋settings.jsonのみではOSレベルの完全なNetwork drive isolationは保証対象外とする。

7. **Web**
   「Cache-only」は削除し、**WebSearch/WebFetch禁止**または**管理者allowlist方式**のどちらかを採用する。

8. **MCP / Hooks**
   MCPおよびHooksはManaged settingsで管理者が許可したものだけ利用可能とする。 ([Claude][4])

9. **Plugin / Skill**
   管理外Plugin、MCP sideload、Skill Shell executionを禁止する。

10. **Managed policy保護**
    Managed settingsを取得できない場合はClaude Codeを起動させず、企業OrganizationへのLoginを強制し、許可するClaude Code Versionを管理する。 ([Claude][5])

11. **プラットフォーム**
    Native Windows版Claude Codeを対象とする。**Native WindowsはSandbox非対応であるため、Filesystem isolationはPermissionベースのbest-effort制御となることを制約事項として明記する。** ([Claude][6])

12. **設定説明**
    実際に投入する `settings.json` はコメント禁止のため、**「本番投入用の有効なJSON」と「設定項目・設定値・目的・理由を記載した説明表」を別々に作成する。** ([Claude][7])

この形なら、次回の `settings.json` 作成時に要件と設定値を1対1で対応させやすく、企業向けの設定設計書としても説明しやすくなります。
