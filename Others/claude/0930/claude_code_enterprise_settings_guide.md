# Claude Code Enterprise：settings.json 設定解説

対象ファイル：`settings.wsl2.enterprise (1).json`  
調査基準日：2026年9月30日  
設定で許容するClaude Codeのバージョン：`2.1.237`  
実機検証：未実施

## 1. 対象範囲と読み方

### 1.1 想定する利用環境

本書は、添付ファイルをClaude Enterpriseの**サーバー管理設定（server-managed settings）**として配布し、ローカルPCのClaude Desktop内で動く**Code機能**へ適用する構成の解説。管理コンソールから設定を配ることと、コードをクラウド上で実行することは別の話。[S02][S03]

ファイル名と`/mnt`等の指定から、Windows PC上の**WSL2内でClaude Codeを実行する構成**を想定する。ただし、添付ファイルだけでは実際のOS・Desktopの版・実行環境の選択は不明。WSL2をPCへ導入しただけで、すべてのCodeセッションが自動的にWSL2実行になるわけではない。[S05][S06]

このJSONによる制御を、DesktopのChat・Cowork・ブラウザー版Claude・PC全体へそのまま拡張して解釈しない。特にCoworkは、Codeと同じサーバー管理設定を取得する仕組みではない。[S02]

### 1.2 公式仕様と固定バージョンの区別

**以下のコメントは、調査時点で公開されている公式仕様の説明。`2.1.237`で全項目が同じように動くと実証したものではない。** 公式資料に明記された導入版・変更版は第4章へ整理した。導入版を特定できなかった項目、固定版との詳細な動作差、導入先端末での実効動作は不明。

「不明」は、推測で有効・無効を断定しないための表記。「意図」「狙い」とした箇所は、設定の組合せから読み取れる目的の説明。実際の企業の設計意図が記録された資料は提供されていない。

出典は本文・コメント中の`[S01]`等で示す。第6章のリンク先は、Anthropicの公式ドキュメント、公式ヘルプ、公式GitHubリポジトリのみ。第三者ブログや一般利用者のIssue投稿は根拠として採用していない。

### 1.3 設定を読むための基本用語

| 用語・表記 | 意味 |
|---|---|
| 管理設定 | 組織の管理者が配る設定。単にクラウドストレージへJSONを置くことではなく、Claude Codeが管理設定として取得する配信経路を指す。[S02][S03] |
| ツール | Claudeが実際の操作に使う機能。例はファイルを読む`Read`、編集する`Edit`、シェル処理を実行する`Bash`。[S07] |
| 権限ルール | 操作前に許可・確認・拒否を決めるルール。基本の優先順位は`deny`、`ask`、`allow`の順。[S07] |
| サンドボックス | コマンドの実行中に、OSの仕組みでアクセス先を制限する隔離環境。許可ダイアログとは別の防御層。[S08] |
| 子プロセス | 元のプログラムから起動する別のプログラム。Claude Codeが起動するシェルや、そのシェルから起動する処理などを指す。[S08][S20] |
| 名前空間／PID名前空間 | プログラムから見えるOS資源を分ける仕組み。PID名前空間は、見えるプロセスとその番号の範囲を分ける。環境変数の削減とは別の隔離機能。[S20] |
| seccomp | Linuxで、プログラムがOSへ要求できる処理を制限する仕組み。本書では主にUnixソケットへのアクセス制限に関係する。[S08][S22] |
| SDK／内部配信サーバー | SDKは、アプリからClaude Codeを組み込んで利用するための開発用の仕組み。内部配信サーバーは、通常の外部MCPサーバーとは接続・管理経路が異なる。[S10] |
| MCP／コネクター | 外部ツールやデータ源をClaudeへつなぐ仕組み。接続できることと、接続後の個々の操作が許されることは別。[S09][S10] |
| スキル／プラグイン／フック | スキルは作業手順等の拡張、プラグインは拡張機能の配布単位、フックは特定イベント時に実行する処理。[S11][S12][S13] |
| `true`／`false` | 真偽値。`disable...`という名前では、`true`が「無効にする」側。すべての`true`が機能の有効化を意味するわけではない。 |
| `"disable"`／`"1"` | 文字列。今回のモード禁止は`"disable"`、環境変数は`"1"`を使用。真偽値の`false`や数値の`1`とは型が異なる。 |
| `[]` | 要素数0の配列。意味はキーごとに異なる。MCP許可リストなら対象0件、サンドボックス除外ならこのファイルから追加する例外0件。 |
| `~/claude_work` | Claude Codeを実行するユーザーのホーム内の作業フォルダー。WSLの例では`/home/taro/claude_work`。Windowsのホームと同一とは限らない。[S06][S08] |
| `Read(//mnt/**)` | 権限ルールの絶対パス指定。`//`がルートを指し、対象はLinux側の`/mnt`配下。`**`は下位フォルダーをまたぐパターン。[S07] |
| `sandbox`内の`/mnt` | 通常の絶対パス。権限ルールとは構文が違うため、先頭を`//`へそろえない。[S08] |

## 2. 全項目のコメント付き設定

**キー・設定値・配列要素・並び順は元ファイルを維持。説明のためのコメントだけを追加した。**

以下は説明用の**JSONC表記**。Claude Codeが読む`settings.json`は標準JSONであり、`//`コメントを含められない。**このコードブロックをコメント付きのまま管理コンソールへ投入しない。** 実際の配布には、元のコメントなしJSONを使用する。[S01]

コメント内の「3.1」等は、本書の補足説明の参照先。

```jsonc
{
  // 【認証方法】claude.aiアカウントを使うログイン経路を指定する。[S04][S23]
  // Enterpriseの組織所属アカウントを使わせるための設定。対象組織は次のUUIDで絞る。
  // 端末全体の個人アカウント利用を禁止する設定ではない。起動経路別の例外は3.1を参照。
  "forceLoginMethod": "claudeai",

  // 【所属組織】claude.aiログインを、このUUIDの組織に制限する。[S23]
  // 単一UUIDの指定ではログイン時の組織選択も自動化する。
  // このUUIDが導入先企業の実際の組織IDかは不明。全組織を許可する記号ではない。
  "forceLoginOrgUUID": "00000000-0000-4000-8000-000000000000",

  // 【管理設定の再取得】起動時に最新のサーバー管理設定を取得するまで待つ。[S03]
  // 取得に失敗した場合、古いキャッシュや管理設定なしで続行せず、Claude Codeの起動を止める。
  // 対象はサーバー管理設定を取得するセッション。初回配布前の端末まで、この値だけで保護できるとは限らない。
  "forceRemoteSettingsRefresh": true,

  // 【起動可能な最小バージョン】2.1.237より古いClaude Codeの起動を拒否する。[S04][S21]
  // インストールや自動更新を実行する設定ではなく、起動時のバージョン検査。
  "requiredMinimumVersion": "2.1.237",

  // 【起動可能な最大バージョン】2.1.237より新しいClaude Codeの起動を拒否する。[S04][S21]
  // 最小値と最大値が同じため、許容するClaude Codeの版は2.1.237のみ。
  // Desktopアプリ自体の版やClaudeモデルの版を固定する設定ではない。
  "requiredMaximumVersion": "2.1.237",

  // 【親アプリからの設定の扱い】優先される管理者設定がある場合、親設定を混ぜない。[S02][S21]
  // 親設定とは、Desktopなど、Claude Codeを起動するアプリがSDK経由で渡す管理設定。
  // JSONの上に書いた行が勝つという意味ではない。また、全設定の最も厳しい値を合成する指定でもない。
  "parentSettingsBehavior": "first-wins",

  // 【権限ルールの管理元】管理設定だけを、権限ルールの設定元にする。[S07][S23]
  // 利用者やプロジェクトのsettings.jsonに追加したallow・ask・denyルールを採用しない。
  // 利用者による個々の承認まで禁止する値ではない。sandboxなど別項目の配列を一括固定する値でもない。
  "allowManagedPermissionRulesOnly": true,

  // 【フックの提供元】利用者・プロジェクトなどのフックを制限し、管理者側のフックに絞る。[S13]
  // 現行仕様には、管理設定で強制有効化されたプラグインのフックなどの例外がある。
  // フック以外に、画面の状態表示やファイル候補を作るstatusLine・fileSuggestion・subagentStatusLineも管理設定に絞る。
  // command形式のプラグインや、認証ヘッダーを作る一部の補助コマンドにも制限が及ぶ。補足は3.8を参照。
  // ただし本ファイルではdisableAllHooksもtrueのため、管理者のフックも含めて無効化する。
  "allowManagedHooksOnly": true,

  // 【MCP許可リストの管理元】管理設定のallowedMcpServersだけを採用する。[S09][S23]
  // 利用者側の許可リスト追加で接続範囲を広げさせない。MCPサーバーを登録・配布する値ではない。
  // 管理設定で定義したサーバーだけを自動接続する、という意味でもない。SDK内蔵サーバーの例外は3.3を参照。
  "allowManagedMcpServersOnly": true,

  // 【接続可能なMCPサーバー】この許可リストの適用対象となるサーバーを0件にする。[S09]
  // 空配列[]は「許可するサーバーなし」。項目を省略して制限しない場合とは異なる。
  // ただしDesktopが内部配信するtype: sdkのコネクターなどは、この検査の対象外。全MCP経路の遮断とは断定できない。
  "allowedMcpServers": [],

  // 【claude.aiコネクター】Claude Code自身がclaude.aiから取得するコネクターを無効化する。[S10]
  // コネクターとは、外部サービスとClaudeをつなぐ連携機能。
  // 現行仕様ではDesktopのLocal／SSHセッションが内部配信するコネクターには効かない。適用範囲は3.3を参照。
  "disableClaudeAiConnectors": true,

  // 【起動時の拡張機能持ち込み】プラグイン・エージェント・MCPの一部の直接読込経路を拒否する。[S11]
  // 現行仕様の対象例は--plugin-dir、--plugin-url、--agents、非SDKの--mcp-config、SDKのplugins指定。
  // .mcp.jsonやSDK内蔵サーバーなどを、この値だけで一括禁止するわけではない。2.1.237での対象経路の完全一致は不明。
  "disableSideloadFlags": true,

  // 【独自カスタマイズ】skills・agents・hooks・mcpの4種類を、承認可能な提供元に絞る。[S11]
  // trueでは4種類すべてが対象。利用者／プロジェクト由来を抑え、プラグイン・管理設定・組込み由来を認める。
  // この値だけでプラグインの配布元を制限するわけではない。次のstrictKnownMarketplacesなどと組み合わせる。
  "strictPluginOnlyCustomization": true,

  // 【プラグイン配布元】許可するマーケットプレイスを0件にする。[S11]
  // 公式マーケットプレイスも含め、対象となる配布元からの追加・インストール等を認めない。
  // 現行仕様では既存プラグインの起動時読込にも適用。ただしclaude.aiからの同期プラグインは別経路であり、全プラグイン停止とは同義ではない。
  "strictKnownMarketplaces": [],

  // 【コマンド実行型のプラグイン配布】command形式の配布元を無効化する。[S11][S13]
  // command形式は、ローカルでコマンドを実行してプラグインの配置先を得る方式。
  // その方式のインストール・更新・読込を止める。通常のBashコマンド全体や全プラグインを止める値ではない。
  "disableCommandPluginSources": true,

  // 【スキルの事前シェル実行】利用者・プロジェクト・プラグイン等のスキル／独自コマンドに埋め込まれた事前実行を止める。[S12]
  // 対象は、スキルの本文を展開するときに実行する!形式のコマンド。実行結果の代わりに無効化を示す文を入れる。
  // 管理者配布スキルと組込みスキルは、この値の対象外。通常のBashツール呼出しを全面禁止する値でもない。
  "disableSkillShellExecution": true,

  // 【組込みスキル】Claude Codeに同梱されたスキルを無効化する。[S12]
  // 組込みスキルと、固定処理を行う通常のスラッシュコマンドは別物。すべての/コマンドを消す値ではない。
  // 公式資料では2.1.205以降、診断用の/doctorは、この値がtrueでも入力して呼び出せる。
  "disableBundledSkills": true,

  // 【動的ワークフロー】スクリプトで複数のサブエージェントをまとめて動かすClaude Codeの機能を無効化する。[S18]
  // ワークフロー用の組込みコマンドや関連スキルも利用できなくなる。
  // OSのタスク実行や任意の業務自動化すべての禁止ではない。現行仕様では、既に実行中のワークフローは継続する。
  "disableWorkflows": true,

  // 【全フック停止】Claude Codeのイベントに応じて自動実行するフックを無効化する。[S13]
  // 今回は管理設定としてtrueを配るため、管理者配布フックも対象。
  // 開始時の準備処理、操作後のチェック、終了時処理などをフックで実装している場合、それらも動かなくなる。
  "disableAllHooks": true,

  // 【外部からのイベント受信】Channels機能のマスタースイッチをオフにする。[S14]
  // 外部のチャットや通知元から、実行中セッションへメッセージを押し込む経路を止める。
  // この組織向け制御では開発用チャネルも停止対象。通常のMCPツール接続そのものとは別の制御。
  "channelsEnabled": false,

  // 【チャネル用プラグインの許可リスト】許可するチャネル用プラグインを0件にする。[S14]
  // 今回はchannelsEnabledがfalseなので、マスタースイッチ側でも受信を止めている。
  // 空配列だけでは開発用チャネルまで完全に止める指定にならないため、両者を区別する。
  "allowedChannelPlugins": [],

  // 【Remote Control】ローカルのClaude CodeセッションをWebやモバイル等から操作する機能を無効化する。[S15]
  // 他の端末から現在のセッションを引き継いで操作する経路の制限。
  // OSのリモートデスクトップ、任意のSSH接続、端末全体のネットワークを止める設定ではない。
  "disableRemoteControl": true,

  // 【Artifacts】Claude CodeのArtifacts機能を無効化する。[S16]
  // セッションの成果物をホスト型Artifactとして公開・共有する機能の制限。通常のローカルファイル作成の禁止ではない。
  // 現行公式資料では非推奨だが引き続き有効なキー。現在はenableArtifact: falseの案内もあるが、本書では元の値を変更しない。
  "disableArtifact": true,

  // 【agent view】バックグラウンドエージェントと、それらを管理するagent viewを無効化する。[S17]
  // 単に一覧画面を隠すだけの値ではなく、関連するバックグラウンドセッションの機能も対象。
  // 通常のサブエージェントをすべて禁止する設定とは区別する。本ファイルにAgentツール全体のdeny指定はない。
  "disableAgentView": true,

  // 【別セッションからの受信】他のClaude Codeセッションから届くメッセージを破棄する。[S19]
  // refuseは「保留して後から承認」ではなく「Claudeに渡さず拒否」の指定。
  // 送信・他セッションの一覧取得は別制御。この値だけで送受信の両方向を禁止するわけではない。
  "crossSessionInbound": "refuse",

  // 【環境変数】Claude Codeの動作に渡す環境変数のまとまり。[S20]
  // ここでは認証情報の子プロセスへの引き継ぎを抑える変数を設定する。
  "env": {
    // 【子プロセスの認証情報削減】認識対象の認証情報を、Bash・フック・標準入出力型MCPの環境変数から除く。[S20]
    // 値は数値の1ではなく文字列の"1"。親のClaude Codeは、API通信に必要な認証情報を保持する。
    // LinuxではBash子プロセスのPID名前空間も分離する。すべての秘密情報やファイルを消す機能ではない。
    // 設定保存先を示す変数の追加除去は2.1.251以降の仕様であり、2.1.237の効果に含めない。
    "CLAUDE_CODE_SUBPROCESS_ENV_SCRUB": "1"
  },

  // 【ツールの利用権限】Claude Codeがツールを使う前の許可・確認・拒否を指定する。[S07]
  // 基本の優先順位はdeny（拒否）→ask（確認）→allow（許可）。OSの権限やサンドボックスは別途適用する。
  "permissions": {
    // 【開始時の権限モード】default、すなわちDesktopのManualに相当する通常確認モードを既定値にする。[S05][S07]
    // ただし、Desktopがフォルダーごとに記憶した選択モードが優先する場合がある。
    // Manual以外をすべて禁止する値ではない。個別のask・denyと次のモード禁止設定を組み合わせる。
    "defaultMode": "default",

    // 【自動判断モードの禁止】autoモードを使えないようにする。[S07]
    // autoは、ユーザーの代わりに安全性判定を行い、承認操作を減らすモード。
    // 指定値は文字列の"disable"。サンドボックス内Bashの自動承認は別設定であり、後段でfalseにする。
    "disableAutoMode": "disable",

    // 【権限確認を飛ばすモードの禁止】bypassPermissionsを使えないようにする。[S07]
    // --dangerously-skip-permissionsによる通常の確認省略も制限する。
    // 指定値は文字列の"disable"。PCで人が直接実行する操作の禁止や、OS管理者権限の剥奪ではない。
    "disableBypassPermissionsMode": "disable",

    // 【明示的な許可】通常の権限確認を省いて認める対象。[S07]
    // ここにない操作が自動的にすべて禁止になるわけではない。deny・ask・モード・既定動作も確認する。
    "allow": [
      // 作業フォルダー配下の読み取りを許可する。[S07]
      // ~/は実行ユーザーのホーム、**は下位フォルダーをまたぐパターン。作業外の読み取りを禁止する行ではない。
      "Read(~/claude_work/**)",

      // 利用者が/cdで移動できる先を、作業フォルダー自身とその配下に絞る。[S07]
      // 現行仕様ではCdのallowを置くと/cdは許可リスト方式になる。Bash内のcdやDesktopの開始フォルダー選択とは別物。
      // このCdルールの詳細が2.1.237でも同じかは不明。導入版を公式資料から特定できなかった。
      "Cd(~/claude_work/**)"
    ],

    // 【実行前の確認】対象ツールを使う際にユーザーの承認を要求する。[S07]
    // 許可するまで待つ制御であり、禁止とは異なる。denyにも一致する場合は承認で解除できない。
    "ask": [
      // 作業フォルダー配下の変更を、実行前に確認する。[S07]
      // Editのパス規則は、組込みの編集・書込みツールに適用。Bashスクリプト内の変更はBash側の承認とsandboxで制御する。
      "Edit(~/claude_work/**)",

      // Bashツールの呼出しに事前承認を要求する。[S07][S08]
      // 後段のautoAllowBashIfSandboxed: falseにより、サンドボックス内でも確認を省かない。
      // 1回の承認対象にスクリプトや複合コマンドを含む場合、内部の処理1件ずつを別々に確認するわけではない。
      "Bash",

      // mcp__で始まるMCPツール全体を確認対象にする。[S07]
      // 現行公式仕様ではask側のツール名ワイルドカードとして使用可能。接続許可を与える行ではない。
      // サーバー側で接続を拒否されたMCPは、このaskを追加しても使えない。2.1.237での同形式の動作確認は未実施。
      "mcp__*"
    ],

    // 【明示的な拒否】一致したツール利用を禁止する。[S07]
    // allowやaskに同時に一致してもdenyが優先。Bashの文字列規則だけで、OS上の同等操作すべてを網羅できるとは限らない。
    "deny": [
      // Linux側の/mnt配下の読み取りを拒否する。[S07]
      // Read/Editのパス規則では、先頭の//がファイルシステムのルートを表す。ネットワーク共有のUNC表記ではない。
      "Read(//mnt/**)",

      // /mnt配下の編集・書込みを拒否する。[S07]
      // WSLでWindowsドライブを/mnt/cなどに置く構成を想定した制限。別のマウント先まで自動的に禁止する値ではない。
      "Edit(//mnt/**)",

      // Claude CodeのPowerShellツールを全面的に拒否する。[S07]
      // WindowsのPowerShellそのものをアンインストールしたり、PC上の全PowerShell実行を止めたりする設定ではない。
      "PowerShell",

      // WebFetchツールによるWebページの取得を拒否する。[S07]
      // Bash経由のHTTP通信やClaude本体のAPI通信まで、この1行だけで止めるわけではない。
      "WebFetch",

      // WebSearchツールによるWeb検索を拒否する。[S07]
      // モデルが既に持つ知識への質問や、許可されたローカルファイルの検索を禁止する行ではない。
      "WebSearch",

      // Bashの入力パラメーターdangerouslyDisableSandboxがtrueの呼出しを拒否する。[S07][S08][S21]
      // 現行の公式構文Tool(param:value)に基づく指定であり、単なるコマンド名の文字列照合ではない。
      // サンドボックス外への再試行を抑える目的。後段のallowUnsandboxedCommands: falseでも再試行経路を止める。
      "Bash(dangerouslyDisableSandbox:true)",

      // .exeを含むBashコマンドの文字列パターンを拒否する。[S07]
      // Windows実行ファイルの起動を抑える狙い。ただし文字列照合であり、すべてのWindows実行経路を保証付きで封じる制御ではない。
      "Bash(*.exe*)",

      // sudoの文字列パターンに一致するBash呼出しを拒否する。[S07]
      // 他ユーザーの権限、典型的には管理者権限でコマンドを実行する操作を抑える狙い。機能の完全禁止ではなく、記載パターンに対する制御。
      "Bash(*sudo *)",

      // suの文字列パターンに一致するBash呼出しを拒否する。[S07]
      // 別ユーザーへの切替えや、別ユーザーとしてのコマンド実行を抑える狙い。機能の完全禁止ではなく、記載パターンに対する制御。
      "Bash(*su *)",

      // doasの文字列パターンに一致するBash呼出しを拒否する。[S07]
      // 別ユーザーの権限でのコマンド実行を抑える狙い。機能の完全禁止ではなく、記載パターンに対する制御。
      "Bash(*doas *)",

      // pkexecの文字列パターンに一致するBash呼出しを拒否する。[S07]
      // 権限管理機構を通じた、別ユーザー権限でのプログラム実行を抑える狙い。機能の完全禁止ではなく、記載パターンに対する制御。
      "Bash(*pkexec *)",

      // mountの文字列パターンに一致するBash呼出しを拒否する。[S07]
      // ファイルシステムをフォルダーへ取り付け、アクセス経路を増やす操作を抑える狙い。機能の完全禁止ではなく、記載パターンに対する制御。
      "Bash(*mount *)",

      // umountの文字列パターンに一致するBash呼出しを拒否する。[S07]
      // 取り付け済みファイルシステムを切り離す操作を抑える狙い。機能の完全禁止ではなく、記載パターンに対する制御。
      "Bash(*umount *)",

      // nsenterの文字列パターンに一致するBash呼出しを拒否する。[S07]
      // 別プロセスの名前空間に入る操作を抑える狙い。機能の完全禁止ではなく、記載パターンに対する制御。
      "Bash(*nsenter *)",

      // unshareの文字列パターンに一致するBash呼出しを拒否する。[S07]
      // 新しい名前空間を作ってコマンドを実行する操作を抑える狙い。機能の完全禁止ではなく、記載パターンに対する制御。
      "Bash(*unshare *)"
    ]
  },

  // 【サンドボックス】主にシェルコマンドとその子プロセスに、OSレベルのアクセス境界を設ける。[S08]
  // 組込みRead/EditツールやDesktopアプリ全体を、この設定だけで同じ境界へ閉じ込めるわけではない。
  "sandbox": {
    // 【隔離の有効化】サンドボックスを有効にする。[S08]
    // Windows PCでは、Claude Codeの実行先がWSL2などの対応環境であることを確認する。Windowsネイティブ実行とは別物。
    "enabled": true,

    // 【隔離できないときの停止】必要な依存ツール不足や非対応環境でサンドボックスが使えない場合、起動を失敗させる。[S08]
    // 警告だけで隔離なしの実行へ進ませないための設定。任意機能のseccompまで必ず有効と保証する値ではない。
    "failIfUnavailable": true,

    // 【隔離内の自動承認を停止】サンドボックス内だからという理由でBashの承認を省略しない。[S08]
    // permissions.askのBashと組み合わせ、隔離と人の確認の両方を使う。サンドボックス自体を無効にするfalseではない。
    "autoAllowBashIfSandboxed": false,

    // 【隔離外への再試行を停止】dangerouslyDisableSandboxを使って隔離外でやり直す経路を認めない。[S08]
    // サンドボックスで失敗したコマンドは、確認に同意しただけではこの経路で再実行できない。
    // ただし明示的なexcludedCommandsは別扱い。すべての除外経路を閉じる値とは同一視しない。
    "allowUnsandboxedCommands": false,

    // 【隔離の除外コマンド】このファイルからは、サンドボックス外で動かす例外を1件も追加しない。[S08]
    // 空配列自体には、他の設定元による例外追加まで禁止する意味はない。
    // 2.1.237での設定合成とENV_SCRUBを含む最終的な除外可否は不明。3.5の実効設定確認が必要。
    "excludedCommands": [],

    // 【ファイルアクセス境界】サンドボックス内のコマンドに適用する読み書きの制限。[S08]
    // permissionsのRead/Editと似た名前でも別の仕組み。ここだけで組込みファイルツール全体を制御しない。
    "filesystem": {
      // 【ファイル隔離を維持】ファイルシステム隔離を無効化しない、という指定。[S08]
      // キー名がdisabledなので、falseが隔離を維持する側の値。enabled: trueと矛盾しない。
      "disabled": false,

      // 【追加の書込み許可】サンドボックス内のコマンドが書き込める場所を追加する。[S08]
      // 既定の作業ディレクトリや一時領域等も考慮されるため、この配列だけで書込先が1か所に限定されるとは限らない。
      "allowWrite": [
        // 実行ユーザーのホーム内にあるclaude_workへの書込みを認める。[S08]
        // フォルダーを作成する設定ではない。OSの権限や、設定ファイル等に対する既定の保護は引き続き適用される。
        "~/claude_work"
      ],

      // 【書込み禁止】許可領域に含まれる場合でも、書き込ませない場所を指定する。[S08]
      // 書込み側ではdenyWriteが禁止の例外として働く。
      "denyWrite": [
        // /mntとその配下への書込みを禁止する。[S08]
        // sandboxのパスは通常の絶対パスなので、ここは//mntではなく/mnt。
        "/mnt"
      ],

      // 【読み取り禁止領域】サンドボックス内から読ませない場所を指定する。[S08]
      // 読み取り側は、禁止領域の中にある特定フォルダーをallowReadで再許可できる。permissionsのdeny優先とは仕組みが異なる。
      "denyRead": [
        // 実行ユーザーのホーム全体を読み取り禁止にする。[S08]
        // ただし後段のallowReadでclaude_workだけを再許可する。ホーム内の他の設定・鍵・ツール用ファイルが読めず、処理が失敗する場合がある。
        "~/",

        // /mntとその配下の読み取りを禁止する。[S08]
        // WSL側でWindowsドライブをここにマウントしている場合、その領域も禁止対象。
        "/mnt"
      ],

      // 【禁止領域内の読み取り例外】denyReadで閉じた領域の一部を、より狭い許可で開く。[S08]
      // ここにない全ファイルを禁止するホワイトリストではない。ホーム外や/mnt外の既定読取範囲は別途残る。
      "allowRead": [
        // ホーム全体の読み取り禁止からclaude_workを除外し、作業用データを読めるようにする。[S08]
        // 結果は「自分のホーム内では原則claude_workだけを読む」という構成。コンピューター全体を同フォルダーだけに限定する指定ではない。
        "~/claude_work"
      ],

      // 【読み取り例外の管理元】管理設定にあるallowReadだけを採用する。[S08]
      // 利用者／プロジェクト設定から、ホーム内の別フォルダーを読み取り例外へ追加させない。
      // この値はallowWriteやexcludedCommandsを同時に固定する値ではない。
      "allowManagedReadPathsOnly": true
    },

    // 【ネットワーク境界】サンドボックス内のコマンドの通信先等を制限する。[S08]
    // Claude本体のAPI通信、Desktop全体、端末上の他アプリを一括制御するファイアウォールではない。
    "network": {
      // 【許可する通信先】サンドボックス内からの接続を認めるホストを列挙する。[S08][S22]
      // 本ファイルが明示するのは次の2件。*.example.comというサブドメインの包括指定は行っていない。
      // 接続先の許可とBash実行の承認は別判定。また、宛先の許可は送信データの安全性を保証しない。
      "allowedDomains": [
        // example.comへの接続を許可対象にする。[S08]
        // この名前が業務で必要な正式な接続先か、例示用のままかは不明。
        "example.com",

        // api.example.comへの接続を許可対象にする。[S08]
        // example.comとは別に明示したAPI用に見えるホスト名。実在・用途・企業の承認状況は不明。
        "api.example.com"

      // 【許可リスト外を即時拒否】未許可ホストへの接続時に、ユーザーへ許可追加を求めず拒否する。[S08]

      "strictAllowlist": true,

      // 利用者／プロジェクトのallowedDomainsやWebFetch(domain:...)のallowによる拡張を認めない。

      // Linux／WSL2での遮断にはseccompが必要。利用できなければ、このfalseだけで全ソケット遮断を保証できない。
      // WSLのWindows実行ファイル起動にも関係するため、.exeの文字列拒否とは別に有効性を確認する。

    // WSL2そのものを無効化する値ではない。
    "enableWeakerNestedSandbox": false
  }
```

## 3. 組み合わせたときの重要な補足

### 3.1 ログイン制限と配布前の端末は別の問題

`forceLoginMethod`と`forceLoginOrgUUID`は、Claude Code側の認証経路・所属組織の制御。OSのサインイン制限、企業外のWebサービスへのアクセス禁止、他アプリからのClaude利用禁止までを実装する設定ではない。[S04][S23]

現行の管理者向け公式資料には、認証経路による違いが明記されている。ターミナルの対話ログイン画面では方式の事前選択にとどまり、claude.aiアカウントの組織検査と、Console・ゲートウェイの認証を同一には扱わない。また、これらの制約を設定した場合、`ANTHROPIC_API_KEY`・`ANTHROPIC_AUTH_TOKEN`・`apiKeyHelper`による認証セッションは起動時に拒否する一方、クラウドプロバイダーの認証には別の適用条件がある。[S04]

今回の**Desktop＋WSL2＋2.1.237**において、どの認証開始経路でどの検査が働くかの完全な確認結果は不明。「このJSONだけで、当該PCの個人Claude利用を完全禁止できる」とは扱わない。特に、ポリシーを受け取っていない別の実行経路まで同じ制約が届くとは限らない。[S03][S04]

また、`forceRemoteSettingsRefresh: true`をサーバーだけに設定しても、**まだ一度も管理設定を受け取っていない端末は、そのフラグ自体を知らない**。初回から取得失敗時に停止させる必要がある場合、公式資料には同じフラグを端末管理側へ先に配る方法が示されている。サーバー管理設定を取得しない種類のセッションへ、このフラグが取得を強制するわけでもない。[S03]

今回のUUIDが正式な組織IDか、管理コンソールが全項目を保存・配信できるか、必要なAPI宛先へ到達できるかは、実際のテナントと端末で確認する事項。

### 3.2 「作業フォルダーのみアクセス可能」にはなっていない

この点は、**ツールの権限**と**サンドボックスの境界**を分けると理解しやすい。次表は、ほかの追加設定を考慮せず、今回のJSONから読み取れる範囲の整理。実際にはOSのアクセス権、既定の保護対象、実行モード、バージョンによる追加条件も働く。[S07][S08]

| 操作 | 今回の指定から読み取れること |
|---|---|
| `Read`で作業フォルダー内の通常ファイルを読む | 明示的なallowの対象。 |
| 組込みファイル編集ツールで作業フォルダー内を変更する | 明示的なaskの対象。禁止ではなく承認待ち。 |
| `Read`で`~/other_project/dummy.txt`を読む | 作業フォルダーのallowに一致しないだけで、このJSONに同パスのRead denyはない。**明示的な禁止とは判断できない。** |
| サンドボックス内のコマンドが同じ`~/other_project/dummy.txt`を読む | ホーム全体のdenyReadに入り、claude_workの例外には入らない。読み取り禁止の対象。 |
| `/mnt`配下を読み書きする | Read/Editのdenyと、sandboxのdenyRead/denyWriteの両方で禁止する構成。 |
| ホーム外かつ`/mnt`外を読む | sandbox.allowReadに書いていない、という理由だけでは禁止されない。残る既定の読み取り範囲を確認する必要がある。 |
| 作業フォルダー外へ書き込む | allowWriteは追加許可。開始ディレクトリ・一時領域等の既定許可もあるため、**claude_work以外への全書込み禁止とは判断できない。** |

**`Read`のallowは、「そこだけが読める」という全体のホワイトリストではない。** 一方、現行仕様の`Cd` allowは、利用者が実行する`/cd`の移動先を許可リスト化する。ただし、`/cd`の制御でDesktopのフォルダー選択やBash内の`cd`まで同時に縛ることはできない。[S07]

また、ホーム内の読み取り制限により、シェル処理が必要とする設定・認証ファイル・ユーザー配下のツールが見えなくなる場合がある。業務に必要なコマンドが失敗したときは、単に承認不足と判断せず、ファイル境界・通信先・認証情報の削減を切り分ける。[S08][S20]

### 3.3 MCPの接続禁止とDesktopコネクターには適用範囲の違いがある

`allowedMcpServers: []`は、この許可リストの検査対象となるMCPサーバーを許可しない設定。一方、公式資料はSDK内で提供されるサーバーの例外を明記している。[S09]

| セッション・連携経路 | 現行公式資料の説明 |
|---|---|
| Claude Code自身がclaude.aiから取得するコネクター | `disableClaudeAiConnectors`の対象。 |
| DesktopのLocal／SSHセッションで、Desktopが内部配信するコネクター | `type: "sdk"`の内部サーバーとして扱う。通常のMCP設定や`managed-mcp.json`はこの経路に適用されない。組織のコネクターツール制御の`blocked`で制限する。 |
| DesktopのWSLセッション | 調査時点の公式資料では、コネクターとプラグインは未対応。将来も使えないというポリシー上の保証ではない。 |

出典：[S10][S06]。これらの経路差が、導入先のDesktopと`2.1.237`の組合せでも完全に同じかは不明。

今回の`permissions.ask`にある`mcp__*`は、残るMCPツールを**確認対象**にするための指定。MCPツールの**全面禁止**ではない。したがって、「MCPの許可リストが空だから、Desktopの外部連携は必ずすべて停止する」とは結論づけない。[S07][S10]

### 3.4 承認と禁止、自動モードと自動承認を混同しない

この設定の意図は、通常のBash利用や作業ファイル編集は人に確認し、禁止対象は承認しても実行させない構成。例えば、Bashの呼出しを承認したとしても、サンドボックス内から未許可ホストへ通信できるようになるわけではない。[S07][S08]

`disableAutoMode`は**権限モードのauto**を禁止する値。`autoAllowBashIfSandboxed`は**隔離されているBashの自動承認**を制御する値。今回、両方の自動化を別々の設定で止めている。[S07][S08]

ただし、`defaultMode: "default"`は開始時の既定値であり、Manualへの完全固定ではない。Desktopが記憶するフォルダー別モードや、利用者のモード選択も確認する。今回のJSONに、すべての代替モードを禁止する指定はない。明示的なask・denyが適用される範囲とは分けて考える。[S05][S07]

### 3.5 サンドボックスの「例外なし」と「例外を追加できない」は異なる

`excludedCommands: []`が表すのは、**このファイルから追加する除外コマンドが0件**という状態。配列の合成や除外に関する扱いは、通常の真偽値の上書きとは異なる。公式資料でも、除外リストの追加を制限する専用の管理元ロックがない点を注意事項として挙げている。[S08]

さらに、現行の変更履歴には、管理ポリシーの条件に応じてプロジェクト側の除外を無視するようにした後続変更もある。**最新クライアントの挙動を、固定した`2.1.237`へそのまま読み替えない。**[S21]

今回の`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`にはLinux側の追加隔離もある。このため、他の設定元に除外がある場合に、**本ファイル全体と組み合わせた`2.1.237`で最終的に何が実行可能になるかは不明**。ここでは未検証の回避方法が存在すると断定せず、逆に全経路を封じたとも断定しない。実効設定と実行結果の確認事項。[S08][S20]

### 3.6 UnixソケットとWSL2は、設定値だけでは有効性が決まらない

`allowAllUnixSockets: false`は、ソケットを無条件で許可しない指定。Linuxでは実際の遮断にseccompを使う。Anthropic公式sandbox-runtime資料は、seccompが利用できなければソケット制限が働かず警告になることを説明している。[S22]

Claude Code公式資料でも、Linuxのseccompは任意の依存機能として扱われている。**Claude Codeが起動できた、またはsandbox.enabledがtrueと表示されたというだけで、Unixソケット遮断まで有効とは判断しない。** WSLからWindows実行ファイルを起動する経路にも関わるため、依存機能の状態を別途確認する。[S08]

なお、sandbox-runtimeの公開リポジトリの最新版と、Claude Code `2.1.237`が使用する実装・版の同一性は不明。本書では、仕組みを補う資料として使用し、対応OS等をそのまま固定版へ転記していない。

### 3.7 ネットワーク許可リストは、端末全体の通信制御や情報持ち出し防止ではない

今回の2つのホストはサンドボックス内の通信先の指定。Claude Code本体のモデルAPI通信や管理設定の取得まで、この2件へ限定するものではない。管理設定の取得には、別途`api.anthropic.com`への到達性が必要。[S08][S03]

`WebFetch`・`WebSearch`のdenyも、それぞれのツールを止める設定。Bash、MCP、Desktop内部機能などの別経路と同一視しない。[S07][S10]

また、宛先を許可したことは、その宛先へ送るデータを許可したこととは別。公式のサンドボックス用プロキシは、既定ではホスト名ベースで制限し、TLS通信の中身を検査しない。今回のJSONには、送信本文の機密情報検査や、組織全体のデータ保持・監査ログ方針を設定する項目もない。[S08]

### 3.8 拡張・自動化・メッセージ機能の停止範囲

`disableAllHooks: true`は管理設定として配るため、`allowManagedHooksOnly: true`で残り得る管理者側のフックも停止する。監査や整形をフックに実装している場合、その処理も止まる点に注意が必要。[S13]

`allowManagedHooksOnly`は、フックの提供元だけを制限する値ではない。現行仕様では、状態表示・ファイル候補・サブエージェント状態表示を作る設定も管理者側に絞る。さらに、コマンド実行型のプラグイン配布元を止め、マーケットプレイスの認証ヘッダーを生成する`headersHelper`も原則として止める。後者には管理設定自身が宣言したマーケットプレイスの例外があり、`disableCommandPluginSources: false`による例外もあるが、今回の値は`true`。[S13]

一方、`strictKnownMarketplaces: []`はマーケットプレイス由来のプラグインを制限する値であり、現行資料ではclaude.ai同期プラグインの別経路が説明されている。組込みスキル、管理スキル、プラグイン、フックを、すべて同じ「拡張機能」として一括解釈しない。[S11][S12]

`disableAgentView`、`disableWorkflows`、`crossSessionInbound`も別機能の制御。特に`crossSessionInbound: "refuse"`だけでは送信を禁止しない。公式資料では、送信・一覧取得の禁止は`SendMessage`・`ListAgents`のdenyで扱う。**この2つのdenyは元ファイルには含まれていない。** 本書のコメント付き設定にも追加していない。[S17][S18][S19]

## 5. 導入時の確認項目

以下は**実施済み結果ではなく、受入確認の観点**。テストには実データや本物の認証情報ではなく、検証用のファイル・アカウント・接続先を使う。

| 観点 | 確認内容 |
|---|---|
| 設定の取得・受理 | 対象セッションの設定元、診断表示、起動ログを確認し、配信成功・パース成功・無効な項目の警告なしを確認する。コマンドや診断画面の利用可否はDesktopと固定版で確認する。[S01][S02][S03] |
| 版と認証 | Desktopが実際に使用する版が`2.1.237`か確認する。承認済み検証環境で組織ID一致・不一致、許容版の範囲外、取得失敗時の停止を確認する。 |
| 実行環境 | WindowsネイティブのLocalとWSL2を区別する。企業管理端末でWSLセッションが許可されているか、必要な依存機能がそろっているかを確認する。[S04][S06][S08] |
| 開始フォルダー | WSLのホームをそのまま開始位置にせず、意図する`~/claude_work`を選ぶ運用と、作業フォルダーの実在・OS権限を確認する。これは本JSONが開始位置を自動設定するという意味ではない。[S06] |
| 読み書き | 同じ検証ファイルについて、組込みRead/EditとBash経由のアクセスを分けて試験する。作業内、ホーム内の作業外、`/mnt`内、ホーム・`/mnt`外を比較する。 |
| 承認 | Bashが隔離内でも確認対象になるか、作業内編集が確認対象になるか、denyに一致する操作が承認で解除されないかを確認する。 |
| 通信 | 許可ホストと未許可ホストを分けて確認する。Bashの承認とホストの許可が別判定になっているか、モデルAPI通信まで遮断したと誤解していないかを確認する。 |
| 外部連携 | MCPの通常接続、Desktop内部配信コネクター、WSLの機能提供状況を分けて確認する。表示されない理由がポリシーなのか、その環境の未対応なのかも記録する。 |
| 拡張・自動実行 | フック、組込みスキル、独自スキル、プラグイン、ワークフロー、agent view、Remote Controlを個別に確認する。 |
| 隔離の実効状態 | 除外リスト、読み取り例外、書込み範囲、通信先の最終値を確認する。Unixソケット遮断はseccompの状態を含めて確認する。 |
| 変更・再起動 | 管理設定の更新後は、既存セッションだけで判断せず新規セッションでも確認する。起動時だけ適用するキーや、既に実行中の処理への影響を分けて記録する。[S02][S03][S18] |
