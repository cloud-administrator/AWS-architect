**前提（これまでに決まったこと）**

- GitLab EE を有償ライセンスなし（Free）で Self-Managed 導入する。GitLab は Azure 上に構築する。
- 認証は Microsoft Entra ID の SAML SSO 必須。外部ベンダーにも社内の Entra ID アカウントを付与し、社員と同じ方式で使う。
- AI エージェントの自動連携は初期リリースから導入する。初期は社内 PC 上のエージェント（ChatGPT デスクトップアプリ等）から操作する。AWS 上の実行環境は後日構築する。

## 1. No.4 グループ構成の詳細 ⇒ おすすめの構成

### 1.1 推奨する階層

要件定義書 4.2 の構成（全社共通領域／組織・業務所有領域）はそのまま使います。そのうえで、次の2点を詳細化します。
- 部門の下に用途別の Subgroup を置く。
- 権限付与用の Group（teams）を任意で置く。

```text
company-development                     会社管理 Top Group（Private）
├─ common                               全社共通領域
│  ├─ platforms                         共通基盤
│  │  ├─ platform-iac                   基盤 IaC（Project）
│  │  ├─ gitlab-platform                GitLab 自体の設定・運用手順（Project）
│  │  ├─ ai-agent-platform              AI エージェント基盤（Project。複数になれば Subgroup）
│  │  └─ citizen-dev-platform           市民開発基盤（Project。複数になれば Subgroup）
│  └─ shared-resources                  共通資材
│     ├─ shared-components              共通部品（Subgroup。部品ごとに Project）
│     └─ standards                      標準資材（Project。開発ルール・雛形・共通手順）
├─ organization                         組織・業務所有領域
│  └─ <部門・業務領域>                   例：sales、hr（Subgroup）
│     ├─ ai-agents                      AI エージェント（Subgroup）
│     │  └─ <業務>-<名称>                個別 Project（例：quote-agent）
│     └─ citizen-dev                    市民開発アプリ／業務フロー（Subgroup）
│        └─ <業務>-<名称>                個別 Project（例：expense-flow）
└─ teams                                権限付与用の Group（任意。Project は置かない）
   └─ <部門>-<役割>                      例：sales-ai-developers
```

**用途別 Subgroup（ai-agents／citizen-dev）を置く理由**

- AI エージェント（外部ベンダーを含むプロ開発）と市民開発では、関わるメンバーが違うことが多い。そのため、最下位 Subgroup の単位で権限を付与できる（IAM-12）。
- 7.1 の「AI 用と市民開発用で Label 体系を分離」を、Issue を導入するときに Subgroup 単位で実現できる。
- 部門内にどちらか一方しかない場合は、用途別 Subgroup を作らず、部門の直下に Project を置いてよい。

**teams Group を置く理由（任意）**

- Free では SAML Group Sync が使えないため、メンバーは GitLab 側で手作業で管理する（IAM-13）。
- 「Group を Project や Group に招待する」機能は Free で使える。
  - 例：`teams/sales-ai-developers` に人を登録し、その Group を対象 Project へ Developer として招待する。
  - 人の出入りは teams Group の1か所を直すだけで済む。
- 利用者が少ないうちは不要。人数が増えた段階で導入する。

### 1.2 階層ごとの権限の付け方

| 階層 | 誰に・どのロールを付与するか | ポイント |
|---|---|---|
| company-development（Top） | GitLab 管理者（2〜3 名）に Owner | 一般利用者は追加しない（配下すべてに継承されるため） |
| common／organization | 追加しない | 同上 |
| common/platforms の各 Project | 基盤担当に Project ごとに Maintainer／Developer | platform-iac に書き込める人は最小限にする |
| common/shared-resources/shared-components | 保守担当に Maintainer、部品を使う開発者に Reporter | 利用者が多い場合は teams の Group を Reporter で招待する |
| common/shared-resources/standards | 保守担当に Maintainer | 可視性を「承認済み Internal」にし、全社員（社内アカウントの外部ベンダーを含む）が参照できるようにする。IAM-04 の「承認済み Internal」の想定例 |
| organization/<部門> | その部門を担当する GitLab 運用管理者に Owner | Project と Subgroup の作成はこの階層の Owner が行う |
| organization/<部門>/ai-agents・citizen-dev | チーム全員が配下の全 Project に関わる場合だけ、ここで付与する | 最下位 Subgroup での付与（IAM-12） |
| 個別 Project | Developer／Maintainer（限定）／Reporter／Planner を個別に付与 | 原則はこの単位で付与する（IAM-12）。外部ベンダーも、担当する Project か最下位 Subgroup にだけ追加する |

### 1.3 おすすめの設定（Free で使えるもの）

**インスタンス全体（管理者設定）**

| 設定 | おすすめ値 | 関連する要件 |
|---|---|---|
| Restricted visibility levels | Public と Internal を制限する。制限した可視性は管理者だけが設定できるため、Internal は申請・承認制にできる | 1.3、IAM-04 |
| Allow new users to create top-level groups | オフ。設定後に追加されたユーザーにだけ効くため、利用開始前に設定する | SCM-05、SCM-07 |
| Default projects limit | 0（個人 Namespace に Project を作らせない） | SCM-07 |
| Protect initial default branches | Fully protected（Developer は Push 不可）。Group 単位の既定保護は有償のため使わない | 5.3、REV-04 |
| Require expiration dates for new access tokens | オン | IAM-09 |
| SSH 鍵の種類の制限 | No.7 で SSH を使う場合は ED25519 等に限定する | 5.4 |

**Group（organization/<部門> 等）**

| 設定 | おすすめ値 | 関連する要件 |
|---|---|---|
| Minimum role required to create projects | Owner（＝GitLab 運用管理者だけが作成できる） | SCM-07 |

**Project（13.1 の初期化で設定）**

| 設定 | おすすめ値 | 関連する要件 |
|---|---|---|
| main の保護 | Allowed to push：No one／Allowed to merge：Maintainers／Force push：禁止 | 5.3、5.4、REV-04 |
| Merge checks | All threads must be resolved をオン | 6.1 |
| Squash | 6.1 の方針に合わせて設定 | REV-03 |
| 後日拡張の機能 | Project の機能設定で無効化する | 1.4 |

インスタンスの既定ブランチ保護（Fully protected）でも、Maintainer は Push できます。「main 変更は MR 経由」を全員に適用するには、Project ごとに Allowed to push を No one にします。

### 1.4 Free では使えないため、運用で補うもの

| 有償の機能 | Free での補い方 |
|---|---|
| メンバー追加のロック（Membership lock） | Project の Maintainer はメンバーを追加できてしまう。Maintainer を限定し、13.1 の棚卸でメンバーを確認する |
| Group 単位の既定ブランチ保護 | Project の初期化で、main の保護を個別に設定する |
| Group Wiki、Group／インスタンスの Issue・MR テンプレート、カスタム Project テンプレート | standards Project に雛形と共通手順を置き、初期化時に各 Project へコピーする |
| SAML Group Sync | teams Group（Free の Group 共有）で手作業のメンバー管理を軽くする |

### 1.5 命名規則の例

- **パス（URL）：** 英小文字・数字・ハイフンだけを使う。表示名は日本語でもよい。
- **部門 Subgroup：** 部門コードを使う（例：`sales`、`hr`）。
- **Project：** `<業務>-<名称>` とする（例：`quote-agent`、`expense-flow`）。
- **作業 Branch・Tag：** 5.4 の規則に従う。

## 2. No.7 Git の認証方式 ⇒ 第1候補は OAuth（Git Credential Manager）

| 優先 | 方式 | 理由 | 注意点 |
|---|---|---|---|
| **第1候補** | OAuth（Git Credential Manager） | 短寿命の OAuth トークンを使い、長期のトークンを PC に置かない（IAM-08・IAM-09）。社内 PC の AI エージェントが Push しても要件を満たす。サインインは Entra ID の SSO 経由のブラウザ認証 | GitLab に OAuth アプリケーションを登録する（リダイレクト URI は `http://127.0.0.1/`、機密でないアプリ、Scope は `read_repository` と `write_repository`）。PC 側では Git Credential Manager にクライアント ID を設定する（`credential.https://<GitLab の URL>.gitLabDevClientId`）。ブラウザでのサインインが必要（Device Flow には非対応）。アクセストークンの有効期限は既定で 2 時間 |
| **第2候補**（Claude の提案。ご確認ください） | SSH 鍵 | 要件定義書の 1.4（SSH を採用する場合の SSH Key 管理）と 5.4（SSH 採用時は鍵種別・失効を設計）で、すでに想定している。ブラウザや Git Credential Manager が使えない環境でも使える | 鍵の種類を ED25519 等に限定する（Free で設定可）。有効期限はユーザーが設定できるが、強制は Ultimate のため、運用ルールで必須にする。退職・異動時に鍵を削除する（IAM-10）。秘密鍵は PC に長く残るので、AI エージェントの Git 操作には使わず第1候補を使う（IAM-09 の趣旨）。SSH ポートの通信経路の確認が必要 |
| 採用しない | Personal Access Token（PAT） | 有効期限が長く（上限の短縮は Ultimate）、PC 上の AI エージェントがそのまま使えるため、IAM-09 と食い違う | Free では PAT の作成自体を止められない（無効化は Premium）。利用ルールで禁止し、棚卸で確認する |

### 補足：社内 PC の ChatGPT デスクトップアプリから Push する場合

| 項目 | 内容 |
|---|---|
| 実行場所 | 「この PC 上（On my computer）」で実行する。クラウド実行（Codex Cloud）は OpenAI 側の環境で動くため、社内 GitLab に届かない |
| 認証 | 第1候補（Git Credential Manager の OAuth）を使えば、エージェントの Push も短寿命の OAuth トークンで行われる |
| Push 先 | 作業 Branch に Push し、`git push -o merge_request.create -o merge_request.target=main` で MR も同時に作る（Free で利用可）。main には直接 Push できない |
| データの扱い | モデルは OpenAI のサーバーで動くため、エージェントが読んだコードや指示の内容は OpenAI に送られる。社内の生成 AI 利用ルール（契約プランでのデータの扱い、扱ってよいデータ区分）を確認する |

## 3. No.8 OAuth を認可するユーザー ⇒ 未決（第1候補：開発者本人、第2候補：専用アカウント）

| 候補 | 向いている使い方 | メリット | 注意点 |
|---|---|---|---|
| **第1候補：開発者本人** | 社内 PC 上の AI エージェント（ChatGPT デスクトップアプリ等）から操作する、初期の使い方 | 追加のアカウントが要らない。Git Credential Manager の OAuth で、本人の認証をそのまま使える。本人の異動・退職でトークンが失効すれば、エージェントも止まる | OAuth の Scope で絞れるのは操作の種類で、対象 Project は絞れない（公式ドキュメントに Project 単位で絞る方法の記載なし）。そのため、本人の権限を必要最小限にする。操作は本人の名前で記録されるので、MR テンプレートに「AI 利用の有無」の欄を設ける等で区別する（REV-07） |
| **第2候補：専用アカウント** | 人に紐づかない常時稼働の連携（後日構築する AWS 上のエージェント等） | 専用アカウントを対象 Project のメンバーにするだけで、権限を限定できる。操作の記録が人と分かれる | Entra ID に人ではないアカウントが必要（全社の認証ポリシー・MFA と調整）。初回の認可で誰かがそのアカウントでログインするため、資格情報の管理者を決める。Refresh Token は認証情報管理基盤で保管する（IAM-09） |

**使い分けの案：** 初期（社内 PC 上のエージェント）は開発者本人、AWS 構築後のエージェントは専用アカウント。要件（IAM-08）はどちらにも対応済みです。
