# 認証・認可方式の比較 — クライアント説明用・詳細版

前の表に、**認証情報の有効期限、更新作業、漏洩時の対応**を加えた版です。

**今回の基本方針は、ユーザー別OAuthによる直接接続です。ゲートウェイは、独自の検査・承認など、追加のセキュリティ要件がある場合に導入します。**

## 1. 認証方式・セキュリティの比較

| 比較項目 | A：External OAuth | B：Snowflake OAuth | C：MCPゲートウェイあり |
|---|---|---|---|
| **構成** | ChatGPT → Snowflake | ChatGPT → Snowflake | ChatGPT → 自社ゲートウェイ → Snowflake |
| **認証・トークン発行の管理** | **Entra ID**が本人認証とトークン発行を担当 | **Snowflake**がトークンを発行。本人認証にはEntra IDのSSOも利用可能 | 前段はOAuthで認証。ゲートウェイからSnowflakeへはPAT等で接続 |
| **ChatGPTが保持・利用する認証情報** | Snowflake用のアクセストークン、発行されたリフレッシュトークン、設定する場合のクライアントシークレット | Snowflake用のアクセストークン、発行されたリフレッシュトークン、custom方式のクライアントシークレット | **ゲートウェイ用のOAuth認証情報**。Snowflake用PAT等は自社側で管理 |
| **MFA・条件付きアクセス** | Entra IDのMFA・条件付きアクセスを利用可能 | SnowflakeまたはSSO先のMFAを利用可能。ただし、Snowflakeでのトークン更新が毎回Entraを通るわけではない | 前段でMFA・条件付きアクセスを利用可能。下流PATの使用時に対話的MFAを繰り返すわけではない |
| **ユーザー別の権限制御** | 本人に対応するSnowflakeユーザー・ロールで制御可能 | 本人のSnowflakeユーザー・ロールで制御可能 | **共通アカウントの場合、個人別認可をゲートウェイで実装する必要がある**。本人別の下流資格情報を使えば、個人単位の権限を維持する構成も可能 |
| **ネットワーク制限** | Snowflake側でChatGPTの送信元IPレンジを許可可能 | 同左 | Snowflakeの許可元を自社の固定IPに限定する設計が可能。ただし、公開ゲートウェイの運用が追加される |
| **監査・利用者の追跡** | Entra認証ログとSnowflakeの個人ログを照合 | Snowflakeの個人ログを確認。SSO利用時はIdPログも照合 | 共通アカウントではSnowflakeのログだけで元の利用者を特定できず、ゲートウェイログとの照合が必要 |
| **主なメリット** | **社内のEntra ID運用に認証・トークン管理を集約しやすい** | **Snowflake中心で構成・管理しやすい** | **独自のデータ検査、承認、利用量制限、横断監査を追加できる** |
| **運用負荷の目安** | **中**：Entraアプリ、ユーザー対応付け、Snowflake設定を管理 | **低～中**：Snowflake中心に、OAuth設定・同意・資格情報を管理 | **高**：認可処理、秘密管理、更新、監視、冗長化、脆弱性対応が追加される |

認証・接続・権限制御の仕様は公式資料に基づきます。「運用負荷」は、今回の構成からの評価です。[docs.snowflake.com](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-agents-mcp?utm_source=chatgpt.com)

> **権限に関する注意：** ユーザー別OAuthでも、公開するツールの権限確認は必要です。例えばCortex Searchは所有者権限で動作するため、元テーブルの個人別アクセス制限が検索時にそのまま再適用されるとは限りません。[docs.snowflake.com](https://docs.snowflake.com/en/user-guide/snowflake-cortex/cortex-search/query-cortex-search-service?utm_source=chatgpt.com)

## 2. 認証情報の有効期限・更新・漏洩時の対応

**用語：** アクセストークンは「アクセス用の利用券」、リフレッシュトークンは「利用券の再発行用の引換券」、クライアントシークレットは「アプリ自身の認証情報」です。PATは、Snowflakeのプログラム接続用トークンです。

| 比較項目 | A：External OAuth | B：Snowflake OAuth | C：MCPゲートウェイあり |
|---|---|---|---|
| **アクセストークンの有効期限** | 一般既定は**60～90分**。実際はEntraの設定・ポリシー等に依存 | custom方式では**既定10分**。**1～60分に設定可能** | 前段OAuthは採用するIdPの設定に依存 |
| **リフレッシュトークン／PATの有効期限** | 通常の非SPAアプリのRTは**既定90日**。フロー・ポリシー等で異なる | custom方式のRTは**既定90日**。通常は**1～90日で設定可能** | 下流PATは**標準既定15日、標準最大365日**。認証ポリシーに従う |
| **自動更新と手動作業** | 有効なRTがあれば、ChatGPTがATを更新。再認証が要求された場合は利用者の操作が必要 | 同左。ATの期限ごとに管理者が手作業する必要はない | 前段OAuthの更新に加え、**下流PATの発行・更新・切り替えを自社で管理** |
| **クライアントシークレットの管理** | 現行のEntra管理手順では最大24か月。Microsoftの推奨は12か月未満。管理者が期限前に更新 | 既定の自動失効期限は公式資料で確認できない。2本のsecretを使った計画的な更新が可能 | 前段OAuthのsecret管理に加え、下流PAT等の管理が必要 |
| **漏洩した場合のリスク** | ATの権限内で不正利用される可能性。RTと必要なclient認証情報の漏洩では、利用が長期化するおそれ | 同左。短いATや、同意取消・単回使用RTなどで軽減可能 | 前段トークンでゲートウェイを操作される可能性。下流PATが漏れると、Snowflakeへの直接利用もあり得る |
| **主な停止・失効方法** | Entraでユーザー停止・セッション取消。必要に応じてSnowflake側でもユーザーを停止 | SnowflakeでOAuthの同意・委任許可を取り消し、必要に応じてユーザーを停止 | 前段の利用を停止し、下流PATを無効化・削除・更新。**共通PATの停止は全利用者に影響** |
| **停止時の注意点** | Entraで停止しても、発行済みATが即時に使えなくなるとは限らない | Entra SSOの停止だけでは、Snowflake発行トークンの停止を保証できない | 前段OAuthだけを止めても、流出したPATの直接利用は止まらない |

期限・更新・失効の仕様は、MicrosoftとSnowflakeの公式資料に基づきます。[learn.microsoft.com](https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens?utm_source=chatgpt.com)

**表を説明する際の補足は、次の3点です。**

- **トークンが自動更新されても、すべての認証情報が自動管理されるわけではありません。** secretやPATの更新・失効には、別の管理作業が残ります。
- **Bの期限は、組織がOAuthクライアントを登録するcustom方式の値です。** built-in OAuthの内部管理や固有の期限は、別途確認が必要です。
- **ChatGPT側に認証情報を全く持たせない構成にはなりません。** Cでもゲートウェイ用のOAuth認証情報は必要です。ChatGPT内部の具体的な保存方式・保存期間・保存地域は、公開資料では確認できません。[help.openai.com](https://help.openai.com/en/articles/20001249?utm_source=chatgpt.com)

## 3. ゲートウェイ導入の判断

| 判断項目 | クライアントへの説明 |
|---|---|
| **ゲートウェイなしで対応できること** | 個人認証、MFA、Snowflakeのロールによる権限制御、送信元IP制限、既存ログによる監査 |
| **ゲートウェイの追加価値** | OpenAIへ送る前の独自データ検査、業務承認、利用量制限、複数MCPを横断した統制、Snowflake用資格情報の自社保管 |
| **追加で負担すること** | システムの構築・保守、認可ロジック、PAT等の更新、ログ管理、障害対応、可用性確保 |
| **共通アカウントを使う場合** | 全員が同じ限定データ・操作を使う用途には適する。個人ごとに閲覧範囲が異なる用途では、権限制御と監査の追加設計が必要 |
| **今回の推奨** | **AまたはBのユーザー別OAuthを基本とする。直接接続では満たせない具体的な要件がある場合にCを追加する** |

**A・Bの選択は、管理方針で判断します。** Entra IDへの集約を重視するならA、Snowflake中心の連携・運用を重視するならB＋Entra SSOが候補です。Aは、採用するChatGPTの接続経路でトークン取得・更新まで動作確認することが条件です。

**ゲートウェイは追加の制御を実装するための仕組みです。現時点の要件では必須とはいえず、共有PATに切り替えるだけで安全性が上がるとは評価できません。**
